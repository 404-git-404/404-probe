## 1. R25 网络判断规则

### 1.1 输入数据与基本约定

- **只判断 TCP**。A 面方块、B 面标记、当前告警都只看 TCP 线路；ICMP 只用于右侧数字（1.8）。A 面方块与 B 面标记只显示**当前所选地址族**（IPv4 / IPv6）；全局的“告警中”只看 **IPv4 TCP**，与页面选了哪个地址族无关（1.9、1.10）。
- **数据来源**：每条线路（卡槽 × 地址族 × 协议）当前的目标（`quality_slots.target_id`）对应的 `staged_probe_v2` 序列（`quality_series`）；读它的 **1 分钟聚合桶**（`quality_buckets`，分辨率 60000，保留 24 小时）。旧语义（含 DNS 的拨号时间）的序列不使用，沿用 v1.0.6 的做法。
- **每个 1 分钟桶里已有的统计量**（`internal/storage/network_quality_rollup.go` 的 `qualityBucketData`）：`Count`（样本数）、`ProbeAttempts`（完整探测数）、`ConnectAttempts` / `ConnectSuccesses`（完成了 Connect 阶段的数 / 其中成功数）、`ValidRTTs`、`NotExecuted`、`Categories`（按 outcome 的计数，例如 `dns_error`、`timeout`）、`IntervalMin/Max`（这些样本的检测间隔）、`ConfigMin/Max`、`SlotMin/Max`（样本带的配置/槽位版本的最小最大值）、`Partial`/`Gaps`（完整性标志），以及 RTT 直方图（格宽 0.25 ms，`bin = round(RTT/0.25)`，范围 0–6000 ms）。**不需要新增存储。** 注意：`Partial`/`Gaps` 只是完整性信息，**不会**自动从 `ConnectAttempts` 里扣除样本（`qualityStatsV2` 的行为），所以“可用分钟”必须在这里显式定义（下面第 4 条）。

#### 1.1.1 评估截止点：进行中的分钟不参与判断（评审 B2）

设评估时刻为 `now`，**评估截止点** `evalEnd = floor((now − 90 秒) / 60 秒) × 60 秒`。只使用满足 `bucket_start + 60 秒 ≤ evalEnd` 的分钟桶；更晚的分钟（包括正在进行的那一分钟）**整分钟不参与**任何判断。A 格、B 标记、右侧数字、当前告警全部使用同一个 `evalEnd`。

- **为什么能排除“未来时钟样本”**：协议允许入库时 `started_at` 比服务器时间最多晚 2 分钟（`internal/protocol/network_quality.go:181–185` 的 `clock_skew` 规则），这样的样本会被写进它自己 `started_at` 所在的分钟桶，聚合桶之后无法再扣除。按上面的截止点，任何参与判断的分钟桶，其中所有样本的 `started_at` 都早于该桶结束时刻 ≤ `now − 90 秒`，因此**不可能含有未来样本**；含有未来样本的分钟（包括那个 `started_at = now + 40 秒` 的样本所在的分钟）此时还没有到截止点。
- **取消了 v1.0.6 对进行中分钟的原始样本回读**（`qualityOpenBucket` 用 `sample_time < end(now)` 过滤）：新设计不读原始样本，由截止点代替；原始样本只保留 8 小时，也不适合作为判断依据。
- **90 秒只是显示宽限，不承诺“最终不变”**：协议还允许补传最多 6 小时内的样本（`too_old` 规则），补传会改写已经参与判断的分钟桶，所以同一段历史在下一次请求时可能变化（颜色、右侧数字、当前告警都可能随补传更新）。最近一格（含 `evalEnd` 之后的时间）标 `in_progress`，提示里写明“数据仍在到达”。
- **后果**：每个方块的数据最多落后实际约 90–150 秒；这是有意的取舍（宁可晚显示，也不把还没有核对完的数据画成颜色）。

#### 1.1.2 可用分钟（评审 B1）：配置/槽位边界与已知缺口不进入任何判断

分钟 `m`（桶起点 `m_start`）只有同时满足下面五条才是**可用分钟**：

1. 在评估截止点之内（1.1.1）。
2. 在该线路**当前开放区间**之内：`m_start ≥ ceil(区间.start_at / 60 秒) × 60 秒`。区间起点所在的那一分钟整分钟不用（它可能混有起点之前的样本，聚合里无法裁剪）。这条把“回看证据”钳制在区间起点之后：同一个目标在关闭再重新打开后继续使用同一条序列（`qualityApplyTx` 里目标指针不变，只是区间关闭再开），所以**必须**由这条规则切断关闭之前的样本，不能只把起点前的格子涂灰。
3. 桶内只有一个配置版本和一个槽位版本：`ConfigMin == ConfigMax` 且 `SlotMin == SlotMax`，且都不为 0（未知版本保守不用）。
4. 槽位版本等于线路当前槽位版本：`SlotMin == quality_slots.revision`（与 v1.0.6 `cardBlock` 的 `mixed` 条件一致，`web/static/network-quality-core.js:305–313`）。
5. 不与任何已知缺口重叠：读取 `quality_gaps`（排除原因以 `storage_pruned:` 开头的），按 `qualityGapOverlaps` 的口径判断（对应 v1.0.6 的 `known_gap`）。缺口在读取时加载一次（与 `qualityStoredGaps` 相同，最多 4096 条）。

**不可用分钟**：不计入 J、S、F，不进入红色规则的任何证据（回看窗口、连续失败序列、覆盖时间、新鲜度），并且**打断**连续失败序列；所在方块标 `partial:true`（提示“含配置变更/缺口”）。分钟内部的边界（同一分钟内配置变更，或同一分钟内关闭后重新打开）无法从聚合里裁剪，所以整分钟不用，**不回读原始样本**。

**与普通未完成探测分开**：`NotExecuted > 0`（有些探测没有完成）**不是**不可用——它只让 J 变小，这一分钟其余的可判断样本照常使用。不能把任何 `Partial` 都当成整桶无效（那样会把 v1.0.6 里仍显示的数据全部丢掉）。

- **方块对齐**：3 分钟方块按 Unix 毫秒对齐到 180000 的整数倍；20 格 = 最近 20 个对齐的 3 分钟窗口（含最后一个 `in_progress` 的格子），共约 57–60 分钟。因为第 2 条，当前开放区间起点之前的格子**没有任何可用分钟**，一律灰，并且这些分钟不会成为起点之后任何格子（包括红色）的证据；这是 N6 的一部分（1.9）。

#### 1.1.3 分钟的三种状态、连续性与格子的唯一结果（第 2 轮评审 F1、F2、F4 的澄清）

以下只是把已定规则写得没有歧义，**没有改变任何已定语义**，也不新增数据库列（判定信息只存在于读取结果里，不持久化）。

**时间轴**：分钟索引 `m = floor(bucket_start / 60000)`，分钟 `m` 覆盖 `[m·60 s, (m+1)·60 s)`（左闭右开）。评估分钟 = 满足 `(m+1)·60 s ≤ evalEnd` 的分钟，最后一个评估分钟 `m_cur = evalEnd / 60000 − 1`。红色规则（1.5.2）在**稠密的分钟时间轴**上求值，每个分钟恰好处于下面三种状态之一：

| 状态 | 定义 | 对红色规则的作用 |
|---|---|---|
| **有数据** | 可用（上面五条）且 `j > 0` | 提供 `(j, b, f)` |
| **空** | 可用但 `j = 0`：没有桶（这一分钟调度没轮到、Agent 没上报），或桶里只有“不判断”的样本（解析失败、取消、未执行…）。**空分钟是正常的状态，不是错误** | 没有证据；**不打断**连续失败序列，序列只受 `GAP`（相邻有数据分钟的最大间隔）限制 |
| **不可用** | 不满足可用五条之一：区间起点之前、桶内版本混合、槽位版本不等于当前、与已知缺口重叠（**没有桶也一样**：缺口覆盖的分钟即使没有桶也是不可用） | 没有证据；**打断**连续失败序列；不进回看窗口的任何计数 |

读取结果里保留整条时间轴的这三种状态（和有数据分钟的 `(j, b, f)`、`IntervalMax`），`redAt`、格子汇总、`partial` 标记都读同一份，不会因为“删掉不可用分钟”而丢掉断点信息。

**格子的唯一结果（F1）**：格子的 `J、S、F` 是格内**可用分钟**之和；不可用分钟的数据整分钟丢弃。三种输入各有唯一的结果：

| 输入 | 结果 |
|---|---|
| (a) **一个分钟桶内混合**：该桶 `ConfigMin ≠ ConfigMax`（或 `SlotMin ≠ SlotMax`） | 这一分钟不可用。格内三个分钟桶都是这样 → `J = 0`，灰，`partial = true` |
| (b) **一个 3 分钟格里有多个纯版本的桶**：分钟 0 的桶配置版本 1，分钟 1、2 的桶配置版本 2，各桶内部一致，槽位版本等于当前、无缺口 | 三个分钟都可用，`J` 等于三者之和（例如每分钟 2 个成功样本 → `J = 6`，绿，`partial = false`）。**配置版本本身的变化不是边界**：配置版本是 Agent 全局的，别的卡槽的改动也会让它变化，不改变这条线路的目标、槽位版本和区间。只有**槽位版本变化**（第 4 条）和**区间边界**（第 2 条）才是边界 |
| (c) **只有一个分钟与已知缺口重叠** | 只有这一分钟不可用，其余两个分钟照常；例如每分钟 2 个成功样本 → `J = 4 ≥ m = 3`，绿，`partial = true`。若剩余的 `J < m` → 灰 |

**连续性是否在边界处断开**：连续失败序列和回看窗口**在不可用分钟处断开**——区间起点之前的分钟、槽位版本边界之前的旧版本分钟、混合分钟、缺口分钟都不是证据，也不能“接起”两侧的失败；**只有配置版本变化而槽位版本、区间不变**时不断开。

**`I`（检测间隔）的取法**：`I(t)` = 分钟 `t−9 … t` 这 10 个分钟里有数据分钟的 `IntervalMax` 的最大值（分钟）；这 10 分钟内没有有数据分钟时取 `quality_config.interval_ms`。（用固定的 10 分钟下限窗口取值，避免 `LOOKBACK` 依赖 `I`、`I` 又依赖 `LOOKBACK` 的循环。）

**解析失败（DNS）与长间隔（F4）**：只有“不判断”样本的分钟是**空分钟**（`j = 0`），**不单独切断**“完全连不上”的序列；序列是否连得起来只由 `GAP` 决定：30 秒（`GAP = 1`）下相邻有数据分钟的间隔必须是 1，所以中间有一个空分钟就断开；60 秒（`GAP = 2`）下容忍一个空分钟，所以“失败、仅 DNS、失败、失败”四个分钟（60 秒间隔）有 3 个失败、覆盖 4 分钟，**会红**；这是已定规则（3 个失败、3 分钟）的直接结果，不是新增例外。
### 1.2 样本分类：正常 / 慢 / 失败 / 不判断

使用的 RTT 是 `connect_ms`（纯 TCP 连接建立时间，**不含 DNS**），与 v1.0.6 的 `pure_connect` 一致。门槛记作 **T**（毫秒，每张卡一个，1.7）。

| 类别 | 定义（TCP，`staged_probe_v2`） | 在聚合桶里怎么数 |
|---|---|---|
| **正常** N | `outcome=success`、探测完整、`connect_ms` 经 0.25 ms 格点化后 **≤ T** | `ValidRTTs − S` |
| **慢** S | `outcome=success`、探测完整、格点化后的 `connect_ms` **> T** | 直方图中 `bin > 4T` 的计数之和 |
| **失败** F | 完成了 Connect 阶段但没连上：`outcome ∈ {timeout, refused, network_error}` 且 `connect_complete`（`timeout` 是探测上限 5 秒内没有连通；`refused` 是被对端拒绝） | `ConnectAttempts − ConnectSuccesses` |
| **不判断** U | 其余全部：解析失败（`dns_error`，含 `dns_timeout/no_address/not_found`）、被取消（`canceled`）、未执行（`not_run`）、本机侧问题（`unsafe_address`、`permission_denied`、`unsupported`、`invalid_config`）、探测不完整（`probe_complete=false`）、时钟校验不过的样本 | `Count − (ConnectAttempts)`；其中 `Categories["dns_error"]` 单独可读 |

要点：
- “可判断样本”记作 **J = N + S + F = ConnectAttempts**。慢与失败合称“坏样本” B = S + F。
- **缺测、未执行、目标异常不进 J**：不当作正常，也不当作失败，不补零、不平滑，与 v1.0.6 已有的严谨处理一致。**配置/槽位边界与已知缺口**按 1.1.2 的“可用分钟”整分钟排除（不是只标 `partial`——`qualityStatsV2` 的 `Partial`/`Gaps` 不会自动从 `ConnectAttempts` 里扣除样本）。
- 配置版本 / 槽位版本在桶里只记录最小最大值：一个桶内出现多个版本时，聚合无法拆分，所以**整分钟不可用**（1.1.2），方块标 `partial:true`；普通的 `NotExecuted > 0`（有些探测没完成）仍然可用。
- **解析失败的样本**（维护者已决定，7.2）：“不判断”（沿用 v1.0.6 的 Connect 失败率只数 Connect 阶段），但持续解析失败时在线路行用文字提示“解析失败”，避免长期显示成灰色“无数据”。
- ICMP 线路不参与方块判断。

### 1.3 3 分钟方块如何从 1 分钟桶得到，直方图能否精确数出“超过任意门槛的样本数”

**得到方式**：方块 = 对齐的 3 个相邻 1 分钟桶相加。`J`、`F` 直接是计数，`S(T)` 是直方图里 `bin > 4T` 的计数；直方图和计数都是可加的，所以三个桶相加和“先合并再数”结果相同。缺一个桶（没有行）就是 0 个样本，不是“正常”。

**精度（实验结论，见附录 A）**：
- 直方图格宽 0.25 ms，`bin = round(RTT / 0.25)`，所以 bin `k` 覆盖 `[0.25k−0.125, 0.25k+0.125)`。对整数毫秒的门槛 T（50–3000，必须是整数），门槛恰好在格点 `k=4T` 上：`bin > 4T` 的样本一定 ≥ T+0.125 ms（一定慢），`bin < 4T` 的样本一定 < T−0.125 ms（一定不慢），**只有 RTT 落在 `[T−0.125, T+0.125)` 的样本分不清**。
- 本设计的**定义**：慢 = “格点化后的 RTT 严格大于 T”，等价于 RTT ≥ T+0.125 ms。与“精确的 RTT > T”只在 `(T, T+0.125)` 这一段不同：这一段的样本被算成正常。
- 实验（每组 100 万个样本，T 取 50/100/200/500/1000/3000）：对平滑分布误差在 0–0.065% 样本之内；对**故意**把 10% 样本堆在 T±0.5 ms 内的对抗分布，最坏 1.25%（门槛附近的样本本来就是“碰巧”的）。对整数毫秒聚集的分布误差为 0。
- **这是格点化口径，不是精确口径，也没有对任意输入的误差上限**（评审 S1）：例如 T=500 ms 而全部 RTT=500.1 ms 时，精确口径 100% 为慢，格点口径 0% 为慢，颜色会变；上面的百分比只是**所选分布下的经验误差**，不是上限证明。真实 RTT 有抖动，几乎不会稳定落在门槛上方 0.125 ms 之内，所以预期实际影响很小，但这是估计，不是保证。
- 结论：不需要新增存储，采用上面显式定义的格点化口径；A 面方块、B 面标记、告警必须共用同一个函数，才能保证一致（1.6）。**必须保留边界测试**：RTT = T−0.25、T−0.125、T、T+0.125、T+0.25 以及 500.1（T=500）时，分类结果恰好是定义所说的那样（见 6.1）。
- 门槛必须是整数毫秒；输入校验拒绝小数（1.7）。若以后要支持小数门槛，格点边界要重新设计。
- 提示里的“最高 N ms”来自直方图最高非空 bin 的上界，是近似值（±0.125 ms），写作“最高约”。

### 1.4 “样本不足 = 灰”的定义（随检测间隔）

设方块期望样本数 `e = 180000 / interval_ms`，`interval_ms` 取该方块三个桶的 `IntervalMax`（保守：间隔刚变长时按更长的算，要求更少）。要求的最少可判断样本数：

`m = max(1, ceil(e / 2))`

| 检测间隔 | e（每 3 分钟） | m | 说明 |
|---|---|---|---|
| 30 秒 | 6 | 3 | 半数以上到达才判断 |
| 60 秒 | 3 | 2 | |
| 90 秒 | 2 | 1 | |
| 120 秒 | 1.5 | 1 | |
| 180 秒 | 1 | 1 | 每格最多 1 个样本 |
| 240 秒 | 0.75 | 1 | 约 25% 的格子没有样本 → 灰 |
| 300 秒 | 0.6 | 1 | 约 40% 的格子没有样本 → 灰 |

规则：`J < m` → **灰**（红色另有规则，见 1.5：`J = 0` 永远灰，`0 < J < m` 在红色成立时显示红）。这就是“没数据或样本不足，不判断”；`J` 只统计可用分钟（1.1.2）。间隔 ≥ 240 秒时，3 分钟一格天然会有空格（灰）：这是物理限制，不是数据丢失；卡片 A 面标题行显示“检测间隔 N 秒”，提示文字说明“检测间隔较长，部分方块没有样本”（维护者已同意接受，7.7）。

### 1.5 方块四种颜色与红色（告警）条件

方块的状态只由**可用分钟**（1.1.2）计算；`J`、`B` 是方块内可用分钟的合计。

| 状态 | 条件 |
|---|---|
| 灰 | `J = 0`（这一格没有任何可用的可判断样本），**或** `0 < J < m`（1.4）且这一格不是红 |
| 绿 | `J ≥ m` 且 `B = 0` |
| 黄 | `J ≥ m` 且 `B ≥ 1`，且**不是红**（单次尖峰、孤立的 ≤2 个坏样本只会是黄） |
| 红 | `J ≥ 1` 且格内**任一可用分钟**的 `redAt` 为真；**条件不再满足时自动解除** |

灰与红的优先级：`J = 0` 的格子永远是灰（即使前一格还是红——没有数据就不判断）；`0 < J < m` 的格子如果红色条件成立则显示红，因为红色靠的是更长的回看窗口里的**密度足够**的证据（见 1.5.2），不是靠这一格本身。

**“持续”的语义（维护者已定，2026-10-23）**：
1. **慢**：坏样本持续约 **5 分钟以上**且占多数 → 红。
2. **完全连不上**：持续 **3 分钟以上** → 红。
3. **孤立的 2 个以内坏样本** → 黄。
- 据此测试机实验的标准答案：E5（完全中断 4 分钟）应红；E7（600 ms 持续 3 分钟，低于 5 分钟）不应红；E1、E2 的孤立尖峰不应红；E3（800 ms，10 分钟）、E4（SYN 丢包 60%，30 分钟）、E6（中断 12 分钟）应红。

#### 1.5.1 选哪个候选：C3（分层），写成确定版本

候选 C1（“K 个不同分钟含坏样本”）、C2（“坏样本占比 + 跨度”）、C3（直接翻译语义）里，**C3 最直接地实现了维护者已定的语义**：语义本身就分成“慢（占多数、持续约 5 分钟）”和“完全连不上（持续 3 分钟）”两种情形，且两个时间长度是写死的；C1 用“不同分钟的个数”间接表示持续时间，在检测间隔变化时含义会漂移；C2 只有占比没有“完全连不上更短”这一档。所以采用 C3，并把“持续”用**有证据支撑的时间覆盖**表示。

第 1 轮评审（B3）指出初版的覆盖时间可以被“两个孤立失败 + 缺测的分钟”凑出来；本版把**证据密度**写进规则（连续性、最少坏样本、窗口内样本密度），仍在 C3 之内，没有改变维护者已定的语义。

#### 1.5.2 确定版本（所有常数写死）

对一条线路、一个**可用**分钟 `t`，只使用 `≤ t` 的可用分钟（不看未来）。每个可用分钟提供 `(j, b, f)` = 可判断样本数、坏样本数（慢 + 失败）、失败数（1.2）。`I` 是检测间隔（分钟；取回看窗口内各桶 `IntervalMax` 的最大值，30 秒 = 0.5）。

| 常数 | 值 | 理由 |
|---|---|---|
| `DEAD_COVER` | **3 分钟** | 维护者语义：完全连不上持续 3 分钟以上 |
| `DEAD_MIN_FAILS` | **3** | 任何红色都至少需要 3 个坏样本——与“孤立的 2 个以内坏样本为黄”的语义一致，使“≤2 个坏样本永不红”对所有检测间隔成立（初版取 2，在 120/300 秒下两个失败就能红，评审 B3） |
| `SLOW_COVER` | **5 分钟** | 维护者语义：慢持续约 5 分钟以上 |
| `SLOW_MAJORITY` | `2b > n`（严格多数） | “占多数”按字面取严格多数；平局不算 |
| `SLOW_MIN_BAD` | **3** | 同上：慢的红色至少 3 个坏样本 |
| `LOOKBACK` | **`max(10 分钟, 6·I)`** | 10 分钟 = 慢的 5 分钟持续时间的两倍，使“过半”有足够样本（30 秒约 20 个、60 秒约 10 个）；间隔长时至少看约 6 个样本（300 秒 → 30 分钟），减少常年偏慢线路在长间隔下偶然的 3/4 过半 |
| `SLOW_MIN_JUDGED` | **`max(4, ceil(0.5 · LOOKBACK / I))`** | 窗口里要有至少一半的**期望样本**才拿它做“多数”的判断（30 秒 ≥10、60 秒 ≥5、120 秒 ≥4、300 秒 ≥4）——这就是证据密度；缺测的分钟（不可用、Agent 掉线）会让 n 变小而无法红 |
| `FRESH` | **`max(2 分钟, 2·I)`** | 证据必须新鲜：最近 `FRESH` 个分钟里没有任何可用且 `j>0` 的分钟（Agent 掉线、断了上报）就**不红** |
| `GAP` | **`max(1, ceil(1.5·I))` 分钟** | 完全连不上的连续失败序列中，相邻两个有样本的分钟的最大间隔：30 秒 → 1（**不允许任何空分钟**，因为 30 秒间隔每分钟应有 2 个样本）；60 秒 → 2（容忍调度抖动造成的一个空分钟）；300 秒 → 8 |
| 覆盖单位 | **`max(I, 1 分钟)`** | 一个样本“代表”它所在的检测间隔，覆盖时间 = `(最后一个坏分钟 − 第一个坏分钟) + max(I, 1 分钟)` |

**红（可用分钟 `t`）当且仅当：** `FRESH` 内有可用且 `j>0` 的分钟，并且下面两条之一成立：

1. **完全连不上**：从 `t` 之前最近的一个有样本的可用分钟开始，向前取“**死分钟**”（`j ≥ 1` 且 `f = j`，即该分钟所有可判断样本都失败）组成的最长序列，要求：相邻两个入选分钟的间隔 ≤ `GAP`，且两者之间**没有不可用分钟**（不可用分钟打断序列）；遇到含成功/慢样本的分钟或间隔过大即停止。序列内失败样本数 ≥ `DEAD_MIN_FAILS`，且覆盖时间 ≥ `DEAD_COVER`。
2. **慢（含失败）占多数**：`LOOKBACK` 窗口（以 `t` 结尾，只含可用分钟）里可判断样本数 `n ≥ SLOW_MIN_JUDGED`、坏样本数 `b ≥ SLOW_MIN_BAD`、`2b > n`，并且窗口内第一个与最后一个含坏样本的分钟之间的覆盖时间 ≥ `SLOW_COVER`。

注意：

- **缺证据与持续失败的区别**：只有“有样本、且样本全是失败”的分钟才算死分钟；**没有样本的分钟不是失败**——30 秒间隔下它会打断序列（评审 B3 的反例：分钟 0 和 2 各 1 个失败、分钟 1 没有样本，得到的是不红）；解析失败等“不判断”样本不进 j，所以只有这类样本的分钟也是空分钟；已知缺口、配置/槽位边界、区间起点前的分钟是不可用分钟，同样打断。
- 长间隔下的孤立失败：300 秒间隔下分钟 0 和 5 各一个失败 = 2 个坏样本 → **不红**（`DEAD_MIN_FAILS=3`）；连续 3 个失败（0、5、10 分钟）才红。
- **不同故障形态的证据**：完全连不上靠“连续、无空档、全失败”；慢靠“窗口里过半且样本密度足够”；两者都不依赖单格的 `m`。

**自动解除**：规则是 `t` 时刻只看过去的无状态函数，不锁存。条件不再满足时，下一个可用分钟起不红（完全连不上：出现第一个成功样本即解除；慢：窗口里坏样本不再占多数时解除，通常在恢复后 3–5 分钟；掉线超过 `FRESH`：变灰）。

**当前状态与历史的区别（评审 B4）**：
- **历史格**保留“当时”的颜色：每个方块的红色按它自己所在分钟的 `redAt(t)` 求值。
- **当前状态**（评审 B4、F3 的确定写法）：`red.active = redAt(m_cur)`，其中 `m_cur = evalEnd / 60000 − 1` 是**最后一个评估分钟**（1.1.3），**不是**“最后一个有数据的分钟”。`redAt` 的新鲜度检查以被求值的分钟为参照：存在分钟 `m ∈ [m_cur − FRESH + 1, m_cur]`（闭区间的分钟索引）是**有数据**分钟，否则不红。因此设最后一个有数据的分钟是 `m_last`，则 `m_cur − m_last ≥ FRESH` 时 `red.active` 为假——最后一批失败不能永远证明自己新鲜。例：30 秒间隔（`FRESH = 2`），分钟 0–3 每分钟两个失败后完全没有上报：`m_cur = 3` 和 `4` 时红，`m_cur = 5` 起不红。故障恢复后，历史里仍有红格，但 `red.active` 已经是假。
- **全局“告警中”**（`alert_active` / `QualityAlertActive`）：见 1.9；它由各条 IPv4 TCP 线路的 `red.active` 合并得到，**不是**“近一小时存在红格”。

**方块上色的需要的历史**：为了给窗口内最早的方块求值，读取分钟桶时多取 `LOOKBACK + 3 分钟` 的前置数据；这些前置分钟同样要先过“可用分钟”的五条规则（区间起点钳制、版本、缺口），不可用的不产生证据。

**求值函数（唯一实现，三处共用）**：
```
redAt(minutes map[int64]minuteStat, t int64, intervalMinutes float64) bool   // minutes 只含可用分钟
```
A 方块、B 面标记、当前告警都调用它（1.10）。

### 1.6 计算放在哪里、什么时候算

**每次请求在 Server 端现算，不持久化。**
- 一次卡片请求（一张卡、一个地址族）读 6 条序列（3 卡槽 × TCP/ICMP）在 `[窗口起点 − (LOOKBACK + 3 分钟), evalEnd)` 内的 1 分钟桶（`WHERE series_id IN (…) AND resolution=60000 AND bucket_start BETWEEN …`，走主键），再读一次相关的 `quality_gaps`，解码、判定可用分钟（1.1.2）、相加、求值（1.5）。
- **截止点代替原始样本过滤**：进行中的分钟不参与（1.1.1），所以不需要像 v1.0.6 的 `qualityOpenBucket` 那样回读原始样本；代价是显示最多落后约 90–150 秒。
- **性能：目前只有微基准，完整接口的性能要在施工后实测（评审 S2）。** 附录 B 的实验只做了“读桶 + 解码 + 累加”，一张卡约 0.43–0.51 ms、31 张卡约 16 ms（单连接、合成数据）。它**不包含**：`redAt`、线路状态与 N6 门控、可用分钟判定（含读取缺口）、前置 `LOOKBACK + 3 分钟` 的读取、JSON 编码、300 秒间隔下更长的回看窗口、真实桶体积、并发浏览器，以及与写入、清理共用同一个数据库连接（`SetMaxOpenConns(1)`）时的竞争。附录 B 里“五个门槛”的计时实际是五次独立查询，不是同一份数据上的纯重算。因此本设计只据此认为“现算是可行的方案”，**不据此承诺任何延迟数字**。
  - **施工后验收**：对完整的 `CardSummary` 和 `Marks`（含上述全部内容）在以下条件下测量并写入报告：31 张卡 × 6 序列、30 / 60 / 300 秒三种间隔、真实大小的桶、20 个并发浏览器各 30 秒一次请求、同时有写入与清理在跑。暂定目标（待实测确认或修正）：总 CPU 随请求线性增长且不明显拖慢上报写入；若不达标，再考虑 10 秒缓存的收益、分批或预聚合，而不是现在假设它们。
- **SSE 下的刷新**：SSE（`/api/v1/web/events`）只推资源遥测，不触发网络质量请求。页面对可见的卡片每 30 秒请求一次（沿用现在的节奏，由 `network-quality-core.js` 的协调器限并发 4）。新接口比 v1.0.6 每卡 6 个 `card-history` 读取更少（1 个请求对 6 个）。
- **请求内缓存**（可选，实测后再定）：以 `(agent, family, settings_revision, 门槛, evalEnd)` 为键、合并同一时刻多个浏览器的请求；键含 `evalEnd` 与 `settings_revision`，因此补传造成的更新在下一个 `evalEnd` 之后可见，门槛或设置变化后立即重算。
- **改门槛后近 1 小时的重算**：分类只依赖当时的门槛和已存的直方图，所以改门槛后下一次请求就按新门槛重新数（`S(T)` 现算），**无需任何数据迁移或回填**。前端保存成功后立即重新读取卡片接口。
- **不持久化的含义**：v1.0.7 没有“告警记录/通知”；红色只是读取时的计算结果。若以后需要告警历史，另立任务。
- 一致性：A 方块、B 面标记、右侧数字、当前告警读同一个 Server 函数的同一份结果（同一个 `evalEnd`、同一组可用分钟）；**前端不再有任何判断逻辑**（`cardCurrent`、`cardBlock`、`latency-mini.js` 里的颜色阈值全部删除）。

### 1.7 每张卡的“慢”门槛设置

- **存储**：`quality_config` 增加列 `slow_threshold_ms INTEGER NOT NULL DEFAULT 500 CHECK(slow_threshold_ms BETWEEN 50 AND 3000)`（schema 35，第 3 节）。每张卡一个，3 个卡槽共用，与检测频率（`interval_ms`）同在这一行。
- **校验**：整数，50–3000（含）；小数、字符串、越界一律 `invalid_threshold`（新增 `QualityErrInvalidThreshold`）。放进现有的 `SaveQualityConfigV4` 请求（`protocol.QualityV4SaveRequest` 增加 `slow_threshold_ms`）。
- **兼容**：请求里**缺省（0 / 不带该字段）= 保持原值**，这样升级时已经打开的旧页面仍能保存（旧页面不知道这个字段）。读模型 `QualityV4Config` 增加 `slow_threshold_ms`，所以新页面总能带上当前值。
- **并发修改**：沿用 `expected_revision`（= `settings_revision`）。门槛属于“设置”，不是“测量”：`qualityApplyTx` 里它改变 `settingsChanged`（`settings_revision` +1），**不改变** `measurementChanged`，所以测量版本 `revision`、Agent 拿到的配置、区间和目标都不动，不会触发 Agent 侧的任何变化（Agent 协议完全不变，旧 Agent 兼容）。
- **必须带上门槛的位置**：`SetQualityEnabledV4`（总开关）里自己构造 `qualityProposal`，需要把当前门槛原样带上，否则总开关会把门槛重置为默认值——这是容易漏的一处，写进测试。
- **界面**：放在卡片现有的网络质量“设置”面板，检测频率旁（`network-quality.js` 的 `buildPanel` 里 `p.interval` 附近），数字输入 + 提示“慢连接的门槛，50–3000 ms，3 个卡槽共用，默认 500”。A 面标题行显示“门槛 N ms”。

### 1.8 卡片右侧数字的口径

窗口：与该行 20 个方块**完全相同的分钟**（最近 20 个对齐的 3 分钟窗口里、`eval_end` 之内的**可用分钟**，1.1），保证“数字”和“方块”看的是同一段数据；不可用分钟（缺口、配置/槽位边界、区间起点前）既不在分子也不在分母。

| 情形 | 显示 | 分子 / 分母 | 说明 |
|---|---|---|---|
| 该卡槽该地址族的 **ICMP 线路在测**（状态 `active`） | `丢包 x.x%`（0 显示 `丢包 0%`） | ICMP 的 Σ(sent − received) / Σsent，只统计完整检测（`window_complete`，3 个包都发出并有结论）；在 1 分钟桶的 `Stats.Sent/Received` 里已有 | 取消、socket 打不开、DNS 失败的检测不进分子也不进分母；ICMP 错误回包算“未收到” |
| ICMP 在测但窗口内 Σsent = 0 | `—`，提示“近 1 小时没有完整的 ICMP 检测” | | |
| **没开 ICMP**（或 ICMP 线路不可用：`icmp_unsupported` 等），TCP 在测 | `失败 x.x%` | TCP 的 Σ F / Σ J（Connect 阶段失败数 / 可判断样本数） | **不叫“丢包”**；解析失败等不判断样本不进分母 |
| 两者都不在测（已关闭、未配置、目标异常…） | `—` 或线路状态文字 | | |
| 只开了 ICMP，没开 TCP | 方块位置显示文字“未测 TCP”；右侧 `丢包 x.x%` | | 定稿说明第 5 节 |

- **数值与分母的展示**：右侧只显示百分比；提示（悬停/键盘聚焦）显示 `近 1 小时 2 / 360 个 Echo（丢 2 个）· N 次检测`（TCP 为 `4 / 120 次连接失败`）。样本很少时（ICMP Σsent < 30，或 TCP J < 10）数字后加“·少”，提示“样本较少，仅供参考”；Σsent < 3 或 J < 3 显示 `—`。
- 颜色：定稿说明只规定“彩色只表示状态”；右侧数字的变色阈值未定，≥10% 深红、≥1% 黄褐、其余中灰（效果图是这样用的；维护者已同意，7.4）。
- v1.0.6 的 33.3%（最近一次检测丢 1 个 Echo）问题随之消失：这里不再有“最近一次”的数值。

2. 区间起点之前的时间灰，并且这些分钟不会成为之后任何格子的证据（1.1.2 第 2 条）；换目标（新的 `target_id`）后旧目标的历史不进入方块。
3. **全局“告警中”** `QualityAlertActive(agent)`（评审 B4、S5）：

   - **不是“近一小时存在红格”**：历史上红过、现在已恢复，`alert_active` 为假（1.5.2 的“当前状态与历史的区别”）。
   - `alert_active`（卡片接口里）、`tcp.red.active`（每条线路）、`QualityAlertActive` 三者用同一个函数、同一个 `evalEnd`，保证一致。
4. 测试：为 N6 的每个关闭原因各写一个用例，结果与 v1.0.6 的 `CurrentTCP` 逐一对照；加上 B4 的“恢复后不再告警”用例（6.1）。

## 2. R30 周期分方向流量

### 2.1 现状

- 套餐用量在表 `agent_plans`（`usage_bytes`、`usage_status`、`cycle_start`、`cycle_end`、`observe_after`…）。**每次上报**在同一个事务里由 `accountPlanTrafficTx`（`internal/storage/plans.go`）累计：`rxDelta = current.RXTotal − old.RXTotal`、`txDelta` 同理（这两个总量已经过 `calculateTrafficDelta` 处理 Agent 重启、计数器归零等情况，并带 `continuityPartial` 标志），按计费方式 `traffic_mode`（`rx` / `tx` / `sum`）选出增量加到 `usage_bytes`。
- 周期边界由 `resolvePlanCycle` 在每次上报时（以及读取时的 `AgentPlanAt`）推进：新周期开始就把 `usage_bytes` 清零、状态置 `partial`。
- 编辑套餐（`PutAgentPlan`）：计费方式/周期种类/周期数/锚点/时区任一改变（`policyUnchanged=false`）就把用量清零；只改价格、配额等不清零；人工校准（`calibration`）把用量设为校准值、状态 `calibrated`；改动当刻之前的增量不跨边界拆分（`observe_after`）。

### 2.2 方案：两个计数器，与 `usage_bytes` 同处累计

**新增列**（`agent_plans`，第 3 节）：
- `cycle_rx_bytes INTEGER NOT NULL DEFAULT 0 CHECK(cycle_rx_bytes >= 0)`、`cycle_tx_bytes` 同。
- `cycle_dir_basis TEXT NOT NULL DEFAULT 'exact' CHECK(cycle_dir_basis IN ('exact','backfill','since'))`：计数器对本周期用量的覆盖情况（见 2.5）。
- `cycle_dir_since INTEGER`（毫秒；`exact` 时为 NULL）：`backfill`/`since` 时界面显示“自 X 起”的 X。

**累计位置**：`accountPlanTrafficTx` 里**同一个 `UPDATE agent_plans …`**，在与 `usage_bytes` **完全相同的条件**内累计：`existed && canAccountDelta && !spansAccountingBoundary`，其中 `canAccountDelta = (phase == planCycleCurrent || phase == planCycleRollback)`（`internal/storage/plans.go:188`）。无论计费方式如何，都把 `rxDelta`、`txDelta` 加到两个新计数器（溢出检查与 `usage_bytes` 一样：加后不得超过 `MaxInt64`）。`usage_bytes` 的逻辑完全不改。要点：（1）**时钟回拨分支（`planCycleRollback`）也累计**——回拨时保留单调的周期游标，继续记录已证实的增量，只把状态置 `partial`；三个量（`usage_bytes`、方向 rx、方向 tx）同增；（2）`planCycleInitialized`、`planCycleAdvanced`（周期刚开始）那一次上报**不累计**（`usage_bytes` 也不累计，它被清零），方向计数同样清零；（3）真正阻断累计的是跨编辑栅栏 `spansAccountingBoundary`（`observe_after`），不是回拨本身。

**清零**：新计数器与 `usage_bytes` **在同一个地方清零，不另设时钟**：
- `resolvePlanCycle` 的 `planCycleInitialized`、`planCycleAdvanced` 分支（周期开始，`usage_bytes=0`）→ 两个计数器 = 0，`basis='exact'`，`since=NULL`。
- `PutAgentPlan` 的 `!policyUnchanged` 分支（用量清零）→ 同上；`policyUnchanged` 且没有校准 → 原样保留三列。
- `AgentPlanAt`（读取时的投影，用于 Web 响应）经过 `resolvePlanCycle`，所以读到的新周期同样是 0，与写入侧一致。

**Agent 重启、计数器归零等**：沿用现有处理——增量来自同一个 `calculateTrafficDelta`，`continuityPartial` 只影响 `usage_status`，不影响计数；因此分方向计数与 `usage_bytes` 永远用同一份增量，不会因这些情况产生偏差。`spansAccountingBoundary`（跨编辑边界的上报）两者同样不计。

**人工校准**：`usage_bytes` 被设为校准值 X（其中包含没有方向信息的历史），所以：两个计数器清零，`basis='since'`，`since=校准时刻`；此后增量照常累计。界面显示“自校准起”的小标记（2.5）。

### 2.3 一致性要求与保证方法

要求（定稿说明第 4 节）：计费方式为“合计”时 ↓ + ↑ = 本周期用量；为“下行/上行”时对应方向 = 本周期用量。

不变量（`basis='exact'` 时必须**逐字节相等**）：

| `traffic_mode` | 不变量 |
|---|---|
| `sum` | `cycle_rx_bytes + cycle_tx_bytes == usage_bytes` |
| `rx` | `cycle_rx_bytes == usage_bytes` |
| `tx` | `cycle_tx_bytes == usage_bytes` |

`basis ∈ {backfill, since}` 时：`since` 时 `f(rx,tx) ≤ usage_bytes`（差额是起算前没有方向记录的部分）；`backfill` 时（迁移回填后已与用量对齐）也要求相等。

保证方法（代码 + 测试）：
1. **代码结构保证**：三个量由同一次增量计算产生、写进同一条 `UPDATE`，没有第二处写入；`usage_bytes` 的增量就是 `f(rxDelta, txDelta)`，所以每一步都保持不变量，不需要事后修正。
2. **数据库层校验（可选的第二道）**：用 `CHECK` 无法表达模式相关的等式；改在迁移末尾和 `database verify` 的数据检查里加一条只读检查（按模式核对 `basis='exact'` 的行），不进热路径。
3. **测试**（6.2）：回拨分支必须与现有记账一致：**现有回归测试补上方向断言**——`plans_test.go:202` `TestPlanUsageAndCycleCursorSurviveClockRollbackAndAdvance`（回拨上报 usage 从 1100 增至 1200、1300：方向计数同增，`sum` 时 ↓+↑ 仍等于 usage）、`plans_test.go:252` `TestPlanClockRollbackBeforeAnchorStillAccumulatesCurrentProof`（回拨到锚点前仍从 100 增至 110）、`plans_test.go:276` `TestObserveAfterStillBlocksRollbackSpanningDeltaAndClearsOnRecovery`（跨编辑栅栏的回拨上报三项都不增，恢复后三项同增）、`plans_test.go:125` `TestAgentPlanAtClockRollbackPreservesCalibratedCycle`（读投影不丢校准后的计数）。评审给出的确定反例也要作为新用例：`sum`，原 usage=150、rx=100、tx=50，回拨上报 rxDelta=30、txDelta=20，不跨 observe_after → usage=200、rx=130、tx=70（三项同增，合计仍等于 usage）。再加属性测试：随机生成上报序列（正常增量、Agent 重启、计数器归零/回退、乱序/重复上报、跨周期边界、跨编辑边界、校准、改计费方式），对三种计费方式在**每一步之后**断言不变量；再加一组固定用例（周期切换那一刻、时区、月末锚点）；以及“旧实现与新实现 `usage_bytes` 逐步相同”的回归（保证没改旧逻辑）。

### 2.5 升级时的回填与“自 X 起”的标注

**能否用 `minute_metrics`（保留 30 天）回填：能，但只对“周期起点仍在 30 天内”的套餐，且有对账。**
- `minute_metrics.rx_total / tx_total` 是每分钟最后一次上报的**设备累计总量**（与 `State.RXTotal/TXTotal` 同源，已处理重启/归零），所以周期内的方向用量 = 当前总量 − 周期起点处的总量。
- **回填步骤（迁移里，对每个有生效周期且 `traffic_mode` 非空的套餐）**：
  1. 起点锚：取 `bucket < cycle_start` 的最后一行（周期开始前最后一分钟的总量）；没有这样的行（周期早于保留期，或设备在周期内才接入）→ 取第一行 `bucket ≥ cycle_start` 并视为不完整。
  2. `rx_b = agent_state.rx_total − 锚.rx_total`，`tx_b` 同（用 `agent_state` 当前的精确总量作终点）；任一为负（计数异常）→ 放弃回填。
  3. **与 `usage_bytes` 对账，只有在有方向证据时才接受**。记 `U = usage_bytes`，容差 `tol = max(16 MiB, U × 1%)`（锚点误差最多一个上报间隔的流量）。所有量用 64 位无符号整数（≤ `MaxInt64`，与 `CHECK` 范围一致），比例分配用 128 位中间值（`math/big` 或 `bits.Mul64/Div64`）和整数向下取整，**不用浮点**。
     - `sum`，记 `S = rx_b + tx_b`：
       - `S == 0`（**零向量，没有方向证据**）：若 `U == 0` → 接受，两个计数器 0，`basis='backfill'`（没有残差，不做任何比例计算）；若 `U > 0` → **不接受**，走下面的 `since` 放弃路径（评审 B5：此时没有可分配的比例，不能凭空创造）。
       - `S > 0` 且 `|S − U| ≤ tol` → 接受。残差 `r = U − S`（可正可负），`rx = rx_b + floorDiv(r × rx_b, S)`，`tx = U − rx`。因为 `U ≥ 0` 所以 `|r| ≤ S`（当 `r<0` 时），保证 `rx ≥ 0` 且 `tx ≥ tx_b·U/S ≥ 0`；`rx + tx == U` 精确成立；不改 `usage_bytes`。
       - 其余 → 不接受。
     - `rx`：`|rx_b − U| ≤ tol` → 接受，`rx = U`，`tx = tx_b`（不涉及比例，`rx_b` 可以为 0）；`tx` 同理，`tx = U`，`rx = rx_b`。其余 → 不接受。
     - 接受 → `basis='backfill'`，`since = 锚点所在分钟`（界面标注起算日）。
     - 不接受（用量里含校准值、缺测、`observe_after` 边界、周期早于保留期、零向量加正用量等）→ 计数器 0，`basis='since'`，`since = 迁移时刻`。
     - **每个套餐写入前，在 Go 里先检查结果是否满足不变量**（非负、整数、`backfill` 时精确相等、不超过 `MaxInt64`）；不满足就把**这个套餐**降级为 `since`，而不是让整库迁移在末尾校验时失败。
     - **必须有的夹具**（评审 B5）：`(U, rx_b, tx_b)` = `(1 MiB, 0, 0)`（`sum`：进入 `since`，不异常、不出现 NaN/负数）、`(0, 0, 0)`（接受，计数器 0）、`(1, 1, 1)`（`S=2, r=−1`：`rx = 1 + floorDiv(−1,2) = 0`，`tx = 1`，精确相等且非负）；再加最大整数附近的值（`U` 接近 `MaxInt64`）。
  4. `usage_status='calibrated'` 的套餐直接走 `since`。
- 回填只读 `minute_metrics` 的几行主键范围（每个套餐 1–2 次点查），与表大小无关。

**界面标注**（基于 `cycle_dir_basis`，A 面第一行“周期”后加小标记，悬停说明）：
- `exact`：无标记。
- `backfill`：小标记“≈”，悬停“本周期的分方向数值由分钟数据回填，精度约一分钟，合计已与周期用量对齐（自 X 日起）”。
- `since`：小标记“*”，悬停“自 X 日起统计；此前的用量没有分方向记录”。
- 下一个周期开始后自动变回 `exact`，标记消失。

**维护者已决定**：校准后分方向计数重新起算并标“*”（7.10）；回填容差与“≈/*”的标注按默认（7.13）。

### 3.3 升级失败回滚路径

- v1.0.6 的路径**仍然成立，不需要修改安装器**：升级前建立受保护的一致性备份（含 SHA-256 记录），迁移（`database migrate-protected`）失败或迁移后验证失败时，安装器恢复旧二进制**并**恢复匹配的数据库备份。v1.0.6 的二进制拒绝打开 schema 更新的库（`checkSupportedSchemaVersion` → `ErrUnsupportedSchemaVersion`），所以“只换回旧二进制、不恢复数据库”本来就不被允许，这一点不变。
- 迁移事务内失败：整个事务回滚，库停在 schema 34，不留半成品（与 migration 34 的测试钩子同样的设计）。
- 迁移成功之后才发现问题（例如分方向用量显示不对）：只能恢复升级前备份（与之前版本的行为一致）；新增的列都有默认值，**对旧程序没有“读不懂”的内容，但旧程序拒绝 schema 35**，这是既有保护。

- **升级时已打开的旧页面**：调用已移除的 `v3/card-history`、`v3/tcp-mini` 得到 410 `client_outdated` 并提示刷新；`PUT v4/config` 不带 `slow_threshold_ms` 仍可保存（缺省 = 保持原值）。

### 4.3 A/B 状态保存与模块等高

- **本地存储**：键 `404-probe:card-face:v1:<agent_id>`，值是 3 个字符，如 `AAB`（机器、流量、网络各一面）；读取时用 `/^[ABab]{3}$/` 校验，不合法一律按 `AAA`。**所有读写包在 `try/catch` 里**（`localStorage` 可能在隐私窗口、被禁用、满了时抛异常），失败就只保存在内存，页面按默认 A 面显示、不报错。键名沿用现有 `404-probe:nq-family:<id>` 的风格；设备被删除时清理对应的键（`sync(ids)` 时）。
- **点击规则**：点击模块空白处只切这个模块；模块内本来可点击的元素（按钮、下拉、网络线路行、`input/select/a`、有 `role=tooltip` 的元素）照常工作且不触发翻面；拖选文字不翻面（`window.getSelection().toString()` 非空或指针移动 > 5 px 时抑制，沿用现有手势代码）。头部 ⇄ 的逻辑：只要有任一模块在 A，全切 B，否则全切 A。
- **悬停提示**：模块背景轻微加深（`:hover`，不加 A/B 角标），`title="点击空白处切换 简要 / 详细"`；不做模块级键盘操作（⇄ 是 `<button>`，键盘可用）。
- **等高**：每个模块一个固定高度的容器：机器 100 px、流量 84 px、网络 176 px（定稿说明），`box-sizing:border-box; overflow:hidden`；A 面和 B 面都是绝对撑满的子容器，**切换只改 `hidden`/`inert`，不改容器高度**，所以卡片和整排网格不跳动。网格（`.agent-grid`）行内高度由内容决定，三个模块定高后卡片定高；文字超长一律 `text-overflow: ellipsis` + `title` 悬停全文（名称、标签、IP 行）。修复 v1.0.6 的“卡槽标签与‘已关闭’重叠”：标签列 62 px 固定宽 + `min-width:0` + 省略号，状态文字放在方块区（不跨列）。

### 4.4 双拉杆组件接口（供 v1.0.8 的 M14 复用）

文件 `range-slider.js`，全局 `RangeSlider`（沿用本项目 IIFE 全局模块的写法，无依赖，不依赖 uPlot）。

```
RangeSlider.create({
  document,                        // 注入，便于测试
  min, max,                        // 可选范围（毫秒时间戳）；max 通常是“现在”
  start, end,                      // 当前选择
  minSpan,                         // 最短跨度（毫秒），v1.0.7 为 10 分钟
  step,                            // 对齐步长（毫秒），v1.0.7 为 60000
  follow,                          // true：end 贴着 max（“跟随现在”），拖动 end 离开 max 后变 false
  labels: {start, end, follow},    // 无障碍文字
  format(ms) -> string,            // 提示/辅助文字的时间格式化
  marks: [{start,end,state}],      // 可选：轨道上的标记条（黄/红），与方块同源
  onChange(range, {follow, source, committed})   // 拖动中 committed=false，松开后 true；用 requestAnimationFrame 节流
}) -> {
  element,                         // 根节点（含轨道、选区、两个拉杆）
  setBounds(min, max),             // 时间前进或范围改变；follow 时 end 随 max 前进
  setRange(start, end, {follow}),
  setMarks(marks),
  getRange(),
  destroy()
}
```
- 行为：两个拉杆独立；整个选区可拖动（保持跨度）；跨度不得小于 `minSpan`；拖到 `max` 附近吸附并恢复 `follow`；触摸与鼠标统一用 Pointer Events（`setPointerCapture`）；拖动时不触发模块翻面（事件 `stopPropagation`，并在 `[role=slider]` 上）。
- 无障碍：两个拉杆是 `role="slider"`，`aria-valuemin/max/now`、`aria-valuetext`（格式化后的时间）、`aria-label`；键盘：←/→ 移动 1 步，Shift+←/→ 移动 10 步，Home/End 到端点；焦点环可见。
- 样式用 CSS 变量（`--rs-track`、`--rs-selection`、`--rs-thumb`…），M14 的大图可以换尺寸与色板。
- v1.0.7 的使用：24 小时轨道（`min = now−24h`，`max = now`），默认选区最近 1 小时且 `follow=true`；`onChange` 驱动 `latency-mini.js` 的视窗（读取同一份 24 小时数据，不重复请求）。

### 4.6 性能

- 只在卡片可见时刷新：沿用现有 `IntersectionObserver` + `document.hidden` 的做法（`network-quality.js` 的 `effective(card)`、`traffic-chart.js` 的 `visible`），不可见的卡片取消在途请求、停止计时。
- A 面：每可见卡每 30 秒 1 个 `v5/card` 请求（现在是每卡 6 个 `card-history`）；B 面可见时才请求 `v3/history`（24 小时曲线）和 `v5/marks`，且只在 B 面不隐藏时；翻回 A 面立即停止并释放（`queue.release(owner)`）。
- 所有读取走现有协调器（并发 ≤4）与 `transportLease`。SSE 触发的 `render()` 只更新文字，不重建 DOM（沿用 `updateDisplay` 的差量更新），20 个方块用固定 DOM 节点只改 `className`/`title`。
- 双拉杆拖动用 `requestAnimationFrame` 节流；曲线只重画不重新读取。

## 附录 B：计算开销实验

方法：在临时数据库里造 31 张卡 × 6 条序列 × 24 小时的 1 分钟桶（267,840 行，平均每桶 78 字节，每分钟 2 个样本，约 2% 慢样本、1% 失败），按 1.6 的读法（一次 `IN (…)` 主键范围查询 + `qualityDecodeBucket` + 直方图求和）计时。
