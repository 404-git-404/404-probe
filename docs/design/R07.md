## 1. 现状调查

### 1.1 数据表（schema 32）

| 表 | 作用 | 来源迁移 |
|---|---|---|
| `quality_config` | 每台 Agent 一行，包括 `revision`（配置版本，乐观锁）、`enabled`（总开关）、`ipv6`（“V6 检测”）、`choices`（v1 三网选择 JSON）、`region_id`（三网共用地区，v2）、`v2_lanes`（12 条通道选择 JSON，v2）、`updated_at` | 23、26 |
| `quality_capability` | 当前会话的能力：`epoch/session_id/supported`、`v2_details`（4 条 lane capability 的 JSON）、`excluded_reason`（如 `platform_excluded:alpine`） | 23、26 |
| `quality_targets` | 目标：`id`（32 位十六进制）、`fingerprint`（`UNIQUE(agent_id,fingerprint)`）、`payload`（`protocol.QualityTarget` 的 JSON）、`created_at`、`retired_at` | 23 |
| `quality_slots` | 通道的当前状态，主键 `(agent_id,slot,family,protocol)`；列有 `revision`（该通道最后一次变化时的配置版本，即“卡槽修订号”）、`target_id`（可为空）、`enabled` | 26 重建 |
| `quality_intervals` | 授权区间，主键 `(agent_id,slot,family,protocol,revision)`；列有 `start_at/end_at`、`config_from/config_until`、`v1_authorized` | 26 重建 |
| `quality_raw` | 原始样本，保留 8 小时；记录 `slot_revision`、`config_revision`、`resolved_ip`、`details_json` | 23、26 |
| `quality_minute` | 旧的分钟聚合，保留 24 小时 | 23 |
| `quality_series` / `quality_sessions` / `quality_receipts` / `quality_retired` / `quality_buckets` / `quality_facts` / `quality_backfill` | 按目标和语义拆分的序列；收据和去重；60s/300s/3600s 桶（分别保留 24h/7d/30d）；回填进度 | 27 |
| `quality_gaps` | Agent 上报的缺测（restart、unknown_gap 等），保留 30 天 | 23 |
| `quality_usage` / `quality_totals` | 每设备、全局计数（由触发器维护），用于配额：每设备 512 个 target、4096 个区间 | 23、27 |
| `tcp_mini_state` / `tcp_mini_high` | M05 的 TCP Mini 告警（按 Agent 汇总所有 IPv4 TCP staged 目标） | 29 |

**迁移 31**（`internal/storage/network_quality_migration31.go`）是移除内置目标时可以照搬的模板：
1. 按存储内容（target payload 的 `source=="manual"`）找出受影响的通道，不依赖配置；
2. 对每个通道：`UPDATE quality_intervals SET end_at=now, config_until=rev` 结束检测，`UPDATE quality_slots SET revision=rev+1, target_id=NULL`；
3. 把 `quality_config.revision` 加 1，重写 choices/v2_lanes；
4. 没有引用的 target 设置 `retired_at`，不删除样本和聚合（历史保留）；
5. 无法解析的 JSON 不阻止启动，按“未设置”处理。

整个 `migrate()` 在一个事务里执行（`storage.go` 第 292–300 行起），失败就全部回滚。

### 1.2 卡槽修订号与配置版本

- `quality_config.revision`：每次“有效保存”加 1。PUT 必须带 `expected_revision`，不相等时返回 `409 revision_conflict`（`ErrQualityConflict`）。如果保存的内容没有变化，直接返回当前配置，版本号不变。
- `quality_slots.revision`（下发给 Agent 时叫 `slot_revision`）：该通道的 target、启用状态或授权最后一次变化时的配置版本。没有变化的通道保留旧值（`qualitySetLaneTx` 第 371 行的跳过逻辑）。
- Agent 上报的每个样本都带 `target_id`、`slot_revision`、`config_revision`。Server 用区间做围栏（`SaveQualityBatch`，`network_quality.go` 第 199–213 行）：必须能找到 `(target_id, slot, family, protocol, revision=slot_revision)` 对应的区间，`config_revision` 在 `[config_from, config_until 或当前版本]` 之内，并且 `started_at` 在 `[start_at−120s, end_at+120s]` 之内，否则 ACK 为 `unauthorized`。
- 前端用 `slot_revision` 识别桶是否跨越了配置边界（`cardBlock` 中的 `mixed`），跨越的桶不混合显示。

### 1.3 目标身份

`qualitySetLaneTx` 把 `protocol.QualityTarget{slot,family,protocol,source,region,host,port,endpoint_version}` 和 agent_id 一起做 sha256，取前 32 位十六进制作为 `target_id`。因此：
- 同一 payload 再次出现时复用旧 target，`retired_at` 被清空，历史接上；
- 地区（region）已经包含在指纹里，改地区本来就会产生新目标；
- ICMP 目标的 `port` 固定为 0（`resolveQualityTarget`）。

### 1.4 Server ↔ Agent 协议

- **能力协商**：Agent 每次 `POST /api/v1/report` 都带头 `X-404-Probe-Quality-Version: 2` 和 `X-404-Probe-Quality-Semantics: staged_probe_v2`（`agent.go` 第 545–546 行）。Server 在响应的 `capabilities` 里回 `network_quality`、`network_quality_v2`、`network_quality_staged`（`app.go` 第 282–284 行）。Agent 只有在 Server 回了能力之后，下一次上报才带 `network_quality_v2` 能力 JSON（4 条 lane）。旧 Server 收到无法识别的 v2 内容会返回 400，Agent 退回 v1 后重发一次（`errQualityV2Rejected`）。
- **配置下发**：
  1. 内联：报告被接受后，Server 把当前会话的配置放进报告响应的 `network_quality`（`qualityReportResponse`），整个响应不超过 4096 字节时才放。Agent 默认每 10 秒上报一次（`cmd/agent` 的 `-interval`），所以配置通常在 10 秒内生效。
  2. 拉取：`POST /api/v1/agent/network-quality/config`，请求体 `{version, epoch, session_id}`，响应不超过 16384 字节；最快每 30 秒一次（`nextFetch`），失败时退避。Agent 用 `DisallowUnknownFields` 严格解码。
  3. 配置超过 4096 字节时（例如 12 条通道都填了很长的域名）走拉取，最长约 10 + 30 秒生效。
- **Agent 校验**（`qualityValidateConfig`，`network_quality_http.go`）：slot 只能是 `telecom/unicom/mobile`；v2 的 active 目标必须满足 `Region==RegionID`、`Source=="catalog"`、`Enabled`、IPv6 目标要求 `IPv6==true`、lane capability 支持；间隔 v1 固定 30000，staged 允许 30000–300000 且是 30000 的倍数；jitter 20，超时 5000。只要有一条不合格，整份配置都被拒绝。
- **调度**（`runQualityWorker`）：每条 active 通道按 `interval×(0.8–1.2)` 执行，最多同时 6 个；配置变化时 `reconcile` 取消已经不存在的通道里正在进行的探测。已经测得的样本留在队列里照常上传；只有授权停止（`stopSerial` 变化）才清空队列。
- **上传**：`POST /api/v1/agent/network-quality`，每批最多 64 个样本、8 个缺测；成功后间隔 10 或 30 秒，失败按退避重试。

### 1.5 Agent 端地址检查（unsafe_address）

- `internal/agent/network_quality_guard.go`：`qualityAddressSafe` 先 `Unmap()`，再调用 `protocol.PublicDestinationIP`；`qualityGuardControl` 挂在 `net.Dialer.Control` 上，每次 connect 之前检查实际要连接的地址。
- `internal/agent/network_quality_staged.go`：每次探测都用 `LookupNetIP(ip4|ip6)` 重新解析，取第一个同族结果检查；不安全就记为 `unsafe_address`，不会再找别的地址，然后拨号字面 IP（Control 会再检查一次）。ICMP 走同样的路径。
- 拦截列表（`internal/protocol/public_egress.go`，快照日期 2026-10-15）：
  - 先要求 `IsGlobalUnicast`，带 zone 的拒绝，`Is4In6` 形式拒绝；
  - IPv4 拒绝 `0.0.0.0/8 10/8 100.64/10 127/8 169.254/16 172.16/12 192.0.0/24 192.0.2/24 192.31.196/24 192.52.193/24 192.88.99/24 192.168/16 192.175.48/24 198.18/15 198.51.100/24 203.0.113/24 240/4`（组播和广播在 IsGlobalUnicast 这一步就被拒绝）；
  - IPv6 只允许 `2000::/3`，并拒绝 `2001::/23 2001:db8::/32 2002::/16 2620:4f:8000::/48 3fff::/20`；
  - `PublicDestinationIP` 额外放行 `64:ff9b::/96`（NAT64 知名前缀），按内嵌的 IPv4 判断。
- 版本差异：guard 和 `PublicDestinationIP` 从 v1.0.4 才有。v1.0.2/v1.0.3 的 Agent 也讲 `staged_probe_v2`，但拨号前不检查地址（已用 `git cat-file` 核实）。

### 1.6 ICMP 能力检测

- `detectICMPSocketBackend` 在 Agent 启动时，对每个地址族依次尝试 datagram ICMP（`udp4/udp6`，取决于 `ping_group_range`）和 raw socket（`ip4:icmp/ip6:ipv6-icmp`，需要 CAP_NET_RAW），能打开就算支持。
- `qualityCapabilities()` 上报 4 条 lane：TCP 总是支持；ICMP 按 backend 是否支持；Alpine 被排除时原因写 `platform_excluded`，不支持时写 `unsupported`。
- Server 在保存时不给不支持的 lane 开区间（`qualitySetLaneTx` 的 `active=false`）；读取时把这类通道显示为 `unavailable`。前端 `laneNotice` 显示“不可用（当前环境无 ICMP 权限）”。
- 已知限制：IPv6 ICMP socket 能打开，不代表本机有 IPv6 连通。目前没有任何“本机无 IPv6”的检测。Podman 容器里如果 `ping_group_range` 允许 datagram ICMP，即使没有 CAP_NET_RAW，也会显示“支持”，要在真机上确认（第 10 节）。

### 1.7 容量预算

`qualityBudget.apply`：存储有压力时关闭检测（state `storage_pressure`）；容量不足时把 staged 间隔放大为 `30000×Scale`（state `capacity_throttled`/`retention_degraded`）。

## 2. 数据模型

### 2.1 概念

```
卡片（每台 Agent 一张）
├─ 总开关 enabled                       — 立即生效，按最后一次保存的配置执行
├─ 检测频率 interval_ms                 — 3 个卡槽共用，30000–300000，30000 的倍数，默认 30000
└─ 卡槽 ×3（slot 键固定为 telecom / unicom / mobile，仅作位置编号 1/2/3）
   ├─ 类型 kind：builtin | custom
   ├─ 地区 region、ISP isp              — 用户标注；404-probe 不核对、不校准、不提醒
   ├─ 目标地址 host、TCP 端口 port
   ├─ 卡槽勾选 slot_enabled
   └─ 4 个子项勾选：ipv4_tcp、ipv4_icmp、ipv6_tcp、ipv6_icmp（默认都不勾选）
```

- **slot 键不改名**。`telecom/unicom/mobile` 继续作为位置编号使用（界面显示“卡槽 1/2/3”）。这样 `quality_slots`、`quality_intervals` 的主键、Agent 的 slot 白名单、历史数据都不用动。ISP 不再由 slot 推出，而是来自 `isp` 标签。
- **内置**：`region` 从 31 个省级地区中选（河北 山西 辽宁 吉林 黑龙江 江苏 浙江 安徽 福建 江西 山东 河南 湖北 湖南 广东 海南 四川 贵州 云南 陕西 甘肃 青海 内蒙古 广西 西藏 宁夏 新疆 北京 天津 上海 重庆），`isp` 从 电信/联通/移动 中选。这份列表作为常量写进 `internal/protocol`，不来自 zstatic。存储时保存 `kind=builtin`，同时保存枚举值（省份名、`telecom|unicom|mobile`）。
- **自定义**：`region`、`isp` 都是自由文本（限制见第 6 节）。
- 卡槽已填地址时，地区和 ISP 必填（P17）。
- 类型、地区、ISP 可以随时直接修改，不影响目标身份、不中断曲线（P1，见 2.3 节）。
- **生效条件**（R07-5）：某个子项被执行，当且仅当 卡槽已填地址 ∧ 卡槽已勾选 ∧ 子项已勾选 ∧ 卡片总开关开启 ∧ Agent 支持该子项（能力、族）∧ Agent 已协商新能力（第 4 节）∧ 无存储压力、平台未被排除。
- 地址是 IPv4 字面量时 v6 子项不可勾选，是 IPv6 字面量时 v4 子项不可勾选（S5）。域名的 v4 子项只解析 A，v6 子项只解析 AAAA。
- 去掉“V6 检测”（`ipv6` 列不再由用户设置）。卡片上的 IPv4/IPv6 显示切换保留。

### 2.2 存储（迁移 34 新增或修改的部分）

新表，每台设备 3 行：

```sql
CREATE TABLE quality_slot_settings(
  agent_id TEXT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  slot TEXT NOT NULL CHECK(slot IN ('telecom','unicom','mobile')),
  kind TEXT NOT NULL CHECK(kind IN ('builtin','custom')),
  region TEXT NOT NULL DEFAULT '' CHECK(length(CAST(region AS BLOB))<=96),
  isp TEXT NOT NULL DEFAULT '' CHECK(length(CAST(isp AS BLOB))<=96),
  host TEXT NOT NULL DEFAULT '' CHECK(length(host)<=253),
  port INTEGER CHECK(port IS NULL OR port BETWEEN 1 AND 65535),
  slot_enabled INTEGER NOT NULL DEFAULT 0 CHECK(slot_enabled IN (0,1)),
  ipv4_tcp INTEGER NOT NULL DEFAULT 0 CHECK(ipv4_tcp IN (0,1)),
  ipv4_icmp INTEGER NOT NULL DEFAULT 0 CHECK(ipv4_icmp IN (0,1)),
  ipv6_tcp INTEGER NOT NULL DEFAULT 0 CHECK(ipv6_tcp IN (0,1)),
  ipv6_icmp INTEGER NOT NULL DEFAULT 0 CHECK(ipv6_icmp IN (0,1)),
  updated_revision INTEGER NOT NULL,
  PRIMARY KEY(agent_id,slot)) WITHOUT ROWID
```

修改：
- `quality_config` 新增 `interval_ms INTEGER NOT NULL DEFAULT 30000 CHECK(interval_ms BETWEEN 30000 AND 300000 AND interval_ms%30000=0)`。`revision`、`enabled` 沿用。`ipv6`、`choices`、`region_id`、`v2_lanes` 成为遗留列：迁移时写成中性值（`ipv6=0`、默认 choices、`region_id=''`、`v2_lanes=NULL`），新代码不再读取。
- `quality_targets` 新增 `identity TEXT`（地址身份，见 2.3，不含标签）和 `created_revision INTEGER`，旧行为 NULL。新 target 的 `payload` 不含标签键。
- 标签（类型、地区、ISP）只存在 `quality_slot_settings`，不另建标签历史表（P1）。
- 12 条通道仍由 `quality_slots`/`quality_intervals` 表示，每个卡槽 4 条（family×protocol），与现在相同。

### 2.3 目标的身份和版本（R07-7；release-decider T1；**维护者决定覆盖 T2**）

- **维护者决定覆盖 T2**（P1）：目标身份只由地址、端口（仅 TCP）、协议族决定。地区、ISP 标签和卡槽类型（内置/自定义）改了不算新目标，可以直接修改，曲线不中断，历史一律按当前标签显示。release-decider 原结论（T2 选 B：标签进入指纹）不再采用。
- **身份键** `identity = sha256(agent_id, slot, family, protocol, host 的规范形式, tcp ? port : 0)`。
  - 本文把“协议族”理解为通道本身的地址族（IPv4/IPv6）和协议（TCP/ICMP）；`slot` 也在键里，因为每个通道属于一个卡槽，不同卡槽填同一地址仍是不同的目标。
  - `kind`、`region`、`isp` **不在键里**。与 v1.0.4 现状（region 在指纹里）不同。
  - ICMP 子项的身份不含端口，所以只改 TCP 端口不会拆开 ICMP 的历史（T1 条件 2）。
- **地址每变一次都新建**（T1 选 B，不变）：`target_id = sha256(identity, created_revision)` 的前 32 位十六进制，`fingerprint` 列存同一个值（满足现有的 `UNIQUE(agent_id,fingerprint)`）。改成 B 再改回 A 时也新建 target，不接回旧历史，卡片曲线不会把切换前的 A 段接回来。
- **不新建的情况**：保存时某个通道新算出的 `identity` 等于其当前 target 的 `identity`，就保留原 target。只改标签、只改类型、只改开关、改频率、取消再勾选子项、总开关变化都属于这种情况。也就是延续现在的跳过逻辑。
- **标签只存一份，在 `quality_slot_settings`**。target 的 `payload` 只保存 Agent 需要的字段（`slot,family,protocol,source:"user",host,port`），不含任何标签键。Web 读模型显示任何 target（当前的或已退役的）时，都按它的 `slot` 取该卡槽**当前的**类型、地区、ISP。
- **只改标签或类型的保存**：
  - `quality_config.revision` 仍然 +1（乐观锁需要它，其他标签页靠它发现变化）；
  - 不新建 target，不关闭也不新开区间，`quality_slots.revision`（`slot_revision`）不变；
  - 下发给 Agent 的配置只有版本号变化，Agent 的 `reconcile` 按 target_id、slot_revision、地址判断通道是否相同，不会取消正在进行的探测。
  - 为了“曲线不中断”，前端判断桶是否跨越配置边界时只看 target_id 和 `slot_revision`，不再看 `config_revision`（见 8.3 节）。
- 配额：每设备 512 个 target 不变。每次改地址最多新建 4 个，大约允许 30 天内改 128 次。只改标签不消耗配额。没有被引用的 target 在历史桶过期后由现有清理逻辑删除（`network_quality_retention.go` 第 94 行）。配额用尽时保存返回 `409 quality_quota`，并要有测试。
- **这样做的影响**：
  - **标签修改不留历史**：数据库里只保存当前标签。无法回答“这个卡槽上周标的是哪个地区”，也无法还原某段数据测量时的标签。
  - **历史随标签一起改名**：把卡槽 1 从“广东 电信”改成“上海 联通”后，卡槽 1 的全部历史（包括它以前填过的地址对应的已退役 target，以及 v1.0.4 遗留的内置目标历史）都按“上海 联通”显示。
  - 卡槽地址清空后标签可以留空（P17 只要求已填地址时必填）；这时该卡槽的历史按“卡槽 N（未标注）”显示。
  - 对 M14 的影响见第 9 节。

## 3. 迁移 34

### 3.0 编号

- 维护者分配：迁移 33 归 R23（YouTube 送中状态，由另一个会话施工），R07 的迁移从 34 开始编号。两者都由 Claude Code 施工，仍然满足“同一版本只由一方新增迁移”。
- 依赖：`migrate()` 按版本号顺序执行 `if version < N`，所以迁移 34 必须排在 R23 的迁移 33 之后，`currentSchemaVersion` 最终为 34。
- 维护者决定（P18）：R23 的迁移 33 先合入，阶段 B 在它之上开发。写第 2 版时，`claude/v1.0.5` 上已有 R23 的迁移 33（`internal/storage/google_status_migration33.go`，`currentSchemaVersion = 33`，提交 `047898701`），阶段 B 以此为基准。
- 迁移 34 只操作网络质量的表，不依赖 R23 迁移 33 的内容。

### 3.1 内容（单事务）

1. 结构：创建 `quality_slot_settings`，`quality_config` 加 `interval_ms`，`quality_targets` 加 `identity`、`created_revision`。
2. **生成内置卡槽**（R07-8）：每个有 `quality_config` 行的 Agent 写 3 行。
   - `kind='builtin'`；
   - `isp` 由 slot 推出（telecom→电信 等，存枚举值）；
   - `region` 由 v1.0.4 的地区推出：先取 `region_id`，为空就取该 slot 在 choices/v2_lanes 里的 `region`。省级 id `["province","河北",null]` 取省名；城市 id `["city","广东","深圳"]` 取所属省份（广东，维护者决定 P2）；省名不在 31 个省级地区里、未选择或无法解析的留空；
   - 标签只写进 `quality_slot_settings`。v1.0.4 遗留 target 的 payload 保持原样不改（其中的 `region` 是旧的 `region_id` 格式），但显示一律按卡槽当前标签（P1），不再读取它；城市名因此不会在界面上出现；
   - `host=''`、`port=NULL`，卡槽和 4 个子项全部不勾选；
   - `updated_revision` 为新版本号。
   - 没有 `quality_config` 行的 Agent 不写，读取时按默认值（3 个空的内置卡槽，无标签）处理。
3. **结束内置线路**（R07-1，照搬迁移 31）：对所有 `quality_slots.target_id IS NOT NULL` 或有开放区间的通道执行：
   - `quality_intervals SET end_at=now, config_until=rev`；
   - `quality_slots SET revision=rev+1, target_id=NULL, enabled=0`；
   - `quality_config SET revision=rev+1, enabled=0, interval_ms=30000`，遗留列写成中性值。
   总开关一并关闭（维护者决定 P3）：“全部不勾选”包括总开关，用户配置好后再开启。
4. 所有 `source='catalog'` 且没有被引用的 target 设置 `retired_at=now`。样本、桶、序列、TCP Mini 状态都不删，历史全部保留。
5. 校验：`quality_usage` 与 `quality_totals` 的区间计数一致，`PRAGMA foreign_key_check` 没有违规（照搬迁移 26），然后写入 `schema_migrations(34)`，`currentSchemaVersion=34`。
6. 读不了的 JSON 不阻止启动：该 Agent 写 3 个空内置卡槽，记一条 Warn（照搬迁移 31）。

### 3.2 可回滚性（release-decider T7：认可）

- 迁移 34 在 `migrate()` 的同一个事务里执行，失败就全部回滚，Server 不会以半迁移状态运行。
- 不提供降级迁移。v1.0.4 二进制遇到 schema 34 会拒绝启动（`checkSupportedSchemaVersion`）。
- 回滚办法 = 停止服务，用 v1.0.4 二进制和升级前的数据库备份一起恢复（`install.sh` 的 `SERVER_UPGRADE_BACKUP`，含 db/WAL/SHM、二进制和单元文件）。升级后产生的数据会丢失。备份只保留最近两次（`backup`、`backup.previous`），再升级两次后这个回滚点就没有了。README 已有“Do not downgrade a migrated database”的先例。
- 阶段 E 在测试 Server 上实际演练一次手工恢复。
- v1.0.5 Agent 连回 v1.0.4 Server 必须正常工作（第 4.3 节），因为 Agent 没有降级路径。

## 4. API 与 Agent 协议

### 4.1 Web API（新增 v4，旧的写接口移除）

| 方法和路径 | 说明 |
|---|---|
| `GET …/network-quality/v4/config` | 读取：`revision, enabled, interval_ms, effective_interval_ms, state, agent_support, capabilities, slots[3], lanes[12]` |
| `PUT …/network-quality/v4/config` | 保存：`{expected_revision, interval_ms, slots[3]}`；**不含 enabled，保存不改变总开关** |
| `PUT …/network-quality/v4/enabled` | 总开关：`{expected_revision, enabled}` |

- `slots[i] = {slot, kind, region, isp, host, port, slot_enabled, ipv4_tcp, ipv4_icmp, ipv6_tcp, ipv6_icmp}`。请求必须正好 3 个且 slot 不重复；严格解码，未知字段返回 400。
- `lanes[j] = {slot, family, protocol, target_id|null, slot_revision, status, condition}`。`status`/`condition` 见第 7 节，由 Server 计算，前端不自行推断。
- `agent_support`：`user_targets`（已协商）、`upgrade_required`（旧 Agent）、`unsupported`（无网络质量能力）、`excluded`（平台排除）。
- **保存**：
  - 在事务外先做输入校验（第 5、6 节）和 Server 侧解析（S2）；
  - 然后在事务内比较 `expected_revision`；
  - 按 2.3 节逐通道决定保留或新建 target，关闭旧区间；
  - 对满足生效条件的通道开新区间；
  - 有效变化时版本号 +1。
  - 只改标签或类型时：版本号 +1，target、区间、`slot_revision` 都不变（2.3 节）。
  - 内容没有变化时返回当前配置，版本号不变（与现在相同）。
  - 频率：30–300 秒，每档 30 秒（维护者决定 P10），其他值返回 `invalid_interval`。
  - 总开关已经开启时，保存的新配置立即生效（“按最后一次保存的配置执行”）；总开关关闭时，只保存，不开区间。
- **总开关**（release-decider T4）：
  - 开启：必须带 `expected_revision`，不一致返回 `409 revision_conflict`。开启等于“执行最后一次保存的配置”，必须是用户看到过的那一版。
  - 关闭：不校验版本，总是成功（最后写入者胜）。关闭是安全的方向，被冲突挡下的话探测会违背用户意图继续运行。
  - 两种情况都让版本号 +1（开或关区间），并返回最新配置。
  - 请求只接受 `enabled` 和 `expected_revision`。
- **并发冲突**：沿用 `quality_config.revision` 这一个乐观锁。
  - 前端收到 409，或者总开关响应里的配置内容与草稿基准不一致时，要把服务器的最新内容一起换成新基准，并提示“配置已被修改”。不能只换版本号，否则下一次保存会悄悄覆盖另一方的改动（T4 条件 2）。
  - 弹窗自己执行的总开关操作成功后，如果返回的卡槽内容与基准相同，只更新基准版本号，草稿保留。
- **错误**：`400 invalid_request` 带字段级 `details[]`，例如 `{slot:"unicom", field:"host", code:"unsafe_address"}`（错误码 `invalid_host`、`reserved_name`、`unsafe_address`、`family_mismatch`、`invalid_port`、`invalid_label`、`label_required`、`invalid_interval`），供界面标注到对应的输入框。`409 quality_quota`、`409 unsupported`、`503 storage_pressure` 沿用。
- **移除**：`GET /api/v1/web/network-quality/catalog`；`PUT …/config`、`PUT …/v2/config`（返回 404，与路由不存在一致）；`GET …/config`、`…/v2/config`、`…/v3/card-config` 由 v4 读取代替。页面和 Server 一起发布（静态文件嵌入二进制），没有旧前端需要兼容。
- **保留**：`v3/card-history`、`v3/history`、`v3/tcp-mini`、`history`、`v2/history`。它们都按 target_id 读取，旧目标的历史照常可读。

### 4.2 Agent 协议：新增协商（release-decider S1 选 A）

- 新 Agent 在 `POST /api/v1/report` 和 `POST …/network-quality/config` 上都加头 `X-404-Probe-Quality-Targets: user_v1`。旧 Server 会忽略未知的头。
- 新 Server 只在本次请求带了这个头时，才在响应能力里回 `network_quality_user_targets: true`。Agent 在下一次上报时才使用新能力字段（照搬 `network_quality_staged` 的两步协商）。
- 只有同时满足“当前会话带了头”和“Server 回了能力”的会话，才会收到自定义目标：
  - target 字段沿用旧结构：`source:"user"`，`region` 为空，`RegionID` 为空；
  - `interval_ms` 取 `max(用户频率, 30000×预算 Scale)`，按 30000 向上取整，最大 300000；
  - `ipv6` = 是否有 v6 子项处于 active。
  - 配置响应不增加任何新字段，旧的解码路径不受影响。
- 新 Agent 的校验：
  - 已协商时，接受 `source=="user"`，不检查 region；
  - 收到目标后用与 Server 相同的规则（放在 `internal/protocol`，代码共用）重新校验主机名，并照旧做每次连接前的公网检查，不信任 Server。
  - 未协商时（连的是 v1.0.4 Server），保持 v1.0.4 的 catalog 校验路径。
- 协商之后才上报的新内容：
  - lane capability 的 `reason:"no_ipv6"`（T5）；
  - staged details 的 `dns_outcome:"not_found"`（T6，Go `IsNotFound`，即 NXDOMAIN 或该族无记录）。
  - 新 Server 的 `QualityCapabilities.Validate` 和 `ValidateDetails` 白名单加入这两个值。旧 Server 不会回能力，新 Agent 也就不会发给它。
- 能力消失时（例如 Agent 降级、头消失）Server 立即改回旧格式：所有用户目标的状态改为 `not_scheduled_legacy`，不再下发。

### 4.3 兼容矩阵

| 组合 | 行为 |
|---|---|
| 旧 Server（v1.0.4）+ 旧 Agent | 不变 |
| 旧 Server + 新 Agent | 头被忽略，没有新能力；Agent 按 v1.0.4 运行（catalog 目标、30 秒）。必测 |
| 新 Server + 旧 Agent（v1.0.2–v1.0.4） | 不下发自定义目标（v1.0.2/1.0.3 没有地址检查，`agent_version` 是自报字符串，不能作安全依据）；配置只用旧字段，`enabled=false` 或目标都不是 active，能通过旧版 `qualityValidateConfig` 和 `DisallowUnknownFields`；卡片显示“需升级 Agent”；CPU、内存、流量上报不受影响 |
| 新 Server + 新 Agent | 全部功能 |

### 4.4 Server 升级前后

- 升级时迁移 34 结束所有内置线路。旧 Agent 队列里已测得的 catalog 样本，`started_at ≤ end_at+120s` 的仍被接受，其余 ACK 为 `unauthorized`，被 Agent 永久丢弃。不会写入新目标。
- **Server 升级到 v1.0.5 之后，所有 Agent 的网络质量检测都会停止，直到用户填写目标（旧 Agent 还要先升级）。** 这是 R07-1 和 S1 的直接后果。维护者已知悉，发布说明中写明（P5）。
- CPU、内存、流量上报完全不受影响（R07-5）。

### 4.5 关闭后的停止与迟到结果（只针对网络质量；release-decider T3 选 A）

- 关闭（总开关关闭、取消勾选、改地址）时，Server 在同一事务里关闭区间（`end_at=now`，`config_until=旧版本`）。Agent 在下一次收到配置时停止调度并取消正在进行的探测：通常 ≤10 秒；配置超过 4096 字节时最多约 40 秒。
- 迟到结果的处理维持现有围栏：
  1. 修订号围栏：样本的 `config_revision` 必须在区间的 `[config_from, config_until]` 内，所以改地址后的迟到样本只会落到旧 target，不会混进新目标；
  2. 墙钟容差：`started_at ≤ end_at + 120s`，超过的 ACK 为 `unauthorized`。
- 关闭前已经测得、关闭后才上传的样本保留，它们是授权期内的真实测量。关闭到 Agent 收到新配置之间（约 10–40 秒）测得的少量样本，也是 Agent 按它最后知道的授权测得的真实数据，同样保留。不采用时钟偏差估计（B）和 Agent 侧按时间丢弃（C），两者都可能误删授权期内的样本。
- 阶段 C 的可选改进：Server 在报告响应能力里附带当前配置版本号（旧 Agent 宽松解码，不受影响）；新 Agent 发现版本更新但没有内联配置时立即拉取，不等 30 秒节流，把最长约 40 秒缩短到约 10 秒。
- “停止上报”的含义（维护者按 release-decider 结论确定，P6）：关闭后不再产生新的测量；关闭前已测得的样本照常补传，最多约 40 秒。

## 5. 地址安全

### 5.1 拦截列表（release-decider S4：维持现状，继续共用）

继续以 `protocol.PublicDestinationIP` 作为唯一的判断点（与公网出口检查共用 `egressDenied`），v1.0.5 不扩充，也不另建网络质量专用列表。
- **IPv4**：见 1.5 节，另有 IsGlobalUnicast 拒绝的组播、广播、未指定、回环。
- **IPv6**：只允许 `2000::/3`，拒绝 Teredo/ORCHID（`2001::/23`）、文档地址（`2001:db8::/32`、`3fff::/20`）、6to4（`2002::/16`）、AS112（`2620:4f:8000::/48`）；ULA `fc00::/7`、链路本地、组播、`::`、`::1` 都不在 2000::/3 之内。
- **IPv4 映射**（`::ffff:a.b.c.d`）：保存时转成 IPv4 字面量，归入 v4 族，按 IPv4 判断（S3）。拨号检查先 `Unmap` 再判断，这一点保留。DNS 返回的映射地址不会被当作 IPv6（v6 子项结果为 no_address，这是正确的：那条路径根本不是 IPv6 连通性）。
- **NAT64**：`64:ff9b::/96` 按内嵌 IPv4 判断。本地用途前缀 `64:ff9b:1::/48`（RFC 8215）继续拒绝，因为 Agent 不知道运营方怎么转换。已知限制：只使用这个前缀的 IPv6-only 主机会得到 `unsafe_address`，写进文档。

### 5.2 Server 保存时检查一次（release-decider S2 选 B）

1. **语法**（S3，规则放在 `internal/protocol`，与 Agent 共用）：
   - 字面 IP：用 `netip.ParseAddr`（它本身拒绝带前导零的 IPv4），不带方括号、不带 zone，保存为 `String()` 的规范形式；映射形式转成 IPv4；然后用 `PublicDestinationIP` 判断，同时判断族与勾选的子项是否匹配。
   - 主机名：
     - 只接受 ASCII（国际化域名填 punycode），统一小写，去掉末尾的点；
     - 总长 ≤253，每段 1–63 个字符，段首尾不能是 `-`，至少两段；
     - 最后一段必须含字母，不能是纯数字，也不能是 `0x` 开头的十六进制（防止 inet_aton 把 `0x7f.1`、`2130706433` 之类解析成 IP）；
     - 出现空白、`_ : / @ [ ] %`、`://` 等字符一律拒绝；
     - 拒绝这些名字和后缀：`localhost`，`.localhost .local .localdomain .internal .home.arpa .invalid .test .example .onion .alt`，整个 `.arpa`，以及 RFC 6762 附录 G 的 `.intranet .private .corp .home .lan`。
   - 端口：十进制 1–65535，不带符号，不带前导零。
2. **解析**：只对本次新增或改动的域名，在事务外用 Server 本机解析器 `LookupNetIP("ip")` 同时查 A 和 AAAA，总时长上限 2 秒。
   - 任何一个结果不是公网地址（按所属族判断）就拒绝（`unsafe_address`）；
   - 解析失败（NXDOMAIN、超时）仍允许保存，由 Agent 兜底；
   - 解析结果不写入数据库，也不写日志。
   - 界面要说明：这次检查只是提示性的，以 Agent 每次连接前的检查为准（Server 与 Agent 的解析器可能不同）。
3. 判断“是不是同一个目标”时，用规范化后的主机（和 TCP 端口）作为键。

### 5.3 Agent 每次连接前重新检查（防 DNS 重绑定）

- 现有 staged 路径已经满足：每次探测都重新解析 → 取第一个同族结果 → `qualityAddressPolicy` → 拨号字面 IP → `Dialer.Control` 再检查。
- **不安全就直接记 `unsafe_address`，不往后找安全的地址，连接失败时也不换下一个地址重试**（S5 条件 2）。
- 新 Agent 对收到的主机名先用 5.2 节的语法规则校验一次，不合格的整份配置都拒绝。

### 5.4 域名同时有 v4 和 v6 解析时

- v4 两个子项（TCP、ICMP）只解析 A，v6 两个子项只解析 AAAA，各自取第一个结果。
- 每个样本都记录 `resolved_ip`。多地址轮换会让历史混入不同 IP，这是可以接受的：“目标是否改变”看配置的地址，不看解析出的 IP，前端曲线也不按 `resolved_ip` 分段（S5 条件 3）。
- 域名没有 AAAA 时，v6 子项连续得到 `not_found`/`no_address`，按第 7 节显示为“目标异常（无 IPv6 解析）”，不计入失败率和丢包率（这些样本本来就不进分母）。

## 6. 自定义地区和 ISP 的输入限制

- 适用于自定义卡槽的 `region`、`isp`。内置卡槽只接受枚举值。
- 长度：1–32 个 Unicode 码点，并且 UTF-8 不超过 96 字节（与表的 CHECK 一致）。卡槽已填地址时两项都必填（`label_required`，维护者决定 P17；内置和自定义都适用）；地址为空时可以留空（迁移产生的空卡槽就是这样）。
- 拒绝（不静默修改）：
  - 首尾空白：前端提交前先去掉，Server 收到带首尾空白的值直接拒绝，保证存储的值稳定；
  - 无效 UTF-8；
  - 控制字符和格式字符：Unicode 类别 Cc、Cf（包括 U+200B–U+200D、U+2060、U+FEFF、双向控制符 U+202A–U+202E、U+2066–U+2069）、行分隔符和段分隔符 Zl/Zp、代理码点、非字符；
  - 除 U+0020 以外的空白（包括 U+00A0、U+3000）；
  - 连续两个以上的空格。
- 不做 Unicode 规范化（不引入 `golang.org/x/text`），写法不同的字符串就是不同的标签。
- 自定义 ISP 写成“电信”也允许，仍然是用户标注；M18 中自定义 ISP 一律归入“其他”。
- **输出转义（防 XSS）**：
  - Server 用 `encoding/json` 输出（默认转义 `< > &`），设置 `Cache-Control: no-store`；
  - 前端只用 `textContent`、`title`/`aria-label` 属性、`<option>` 的 `textContent` 和 SVG `<title>` 的 `textContent`，禁止 `innerHTML` 和拼接 HTML；
  - 标签不进入日志、URL 和 CSS 选择器；
  - 阶段 D 加一个测试：标签为 `<img src=x onerror=…>`、含双向控制符的值，在卡片、弹窗、Mini 图例、详情页下拉里都原样显示为文本（或被 Server 拒绝）。

## 7. 状态判定

### 7.1 每个子项的状态（Server 计算 `status` + `condition`，前端只负责显示）

按以下优先级，取第一个命中的：

| 优先级 | 状态 | 条件 | 是否计入失败或丢包 |
|---|---|---|---|
| 1 | 设备已撤销/暂停 | 沿用现有逻辑 | — |
| 2 | 需升级 Agent / 不支持 | `agent_support` 不是 `user_targets` | — |
| 3 | 平台排除、存储压力 | 沿用 `excluded_reason`、`storage_pressure` | — |
| 4 | **已关闭**（R03-2） | 卡片总开关关闭。卡片显示“已关闭”，不再显示地区和“暂无有效 RTT” | 否 |
| 5 | **未配置目标** | 卡槽地址为空 | 否 |
| 6 | **未启用** | 卡槽未勾选或子项未勾选；卡片显示“未启用”（维护者决定 P9） | 否 |
| 7 | **不支持 ICMP** | ICMP 子项且 lane capability `supported=false`（例如容器内 CAP_NET_RAW 受限）。勾选框禁用；已保存的勾选保留但不调度 | 否 |
| 8 | **本机无 IPv6** | v6 子项且 lane capability `reason=no_ipv6`（见 7.2） | 否 |
| 9 | **目标异常** | 见 7.3 | 否（显示层；统计口径不变） |
| 10 | 正常、失败、过期、未知 | 沿用 `cardCurrent`（staged 当前样本、新鲜度预算、目标不匹配）；“目标不匹配”只比较 target_id 和 `slot_revision`，不比较 `config_revision`，只改标签后当前值不会变成“未知”（2.3 节） | 按现有口径 |

### 7.2 本机无 IPv6（release-decider T5 选 A，附条件）

- 判定只看地址：Agent 本机除回环和链路本地外没有任何 IPv6 地址，或者 IPv6 被整个禁用，才算“无 IPv6”。ULA（`fc00::/7`）算作“有”，因为 Podman 容器可能通过 NAT66 用 ULA 出网。
- 滞后：持续 ≥5 分钟（或从 Agent 启动起一直如此）才确认“无 IPv6”。确认之前照常探测、照常计失败。确认之后 v6 子项不再执行，也不计失败。地址一出现立即恢复。
- 有地址但没有路由时照常探测、照常计失败，如实反映“IPv6 坏了”。不按 ENETUNREACH 归类（B 会把路由临时撤销这类真实故障藏起来）。
- 经新协商后才上报（`reason:"no_ipv6"`）。旧 Agent 不上报，行为与现在一样。
- 误判风险：有全局地址但上游根本不通，会显示为失败而不是“无 IPv6”。这是有意为之。

### 7.3 目标异常（release-decider T6；判据和风险见下表；最终结论见第 12 节 P7）

目标是每张卡片各自的，不能用“所有 Agent 都失败”来判断。v1.0.5 采用以下判据，**只影响显示，失败率和丢包率的口径不变**：

| 判据 | 是否采用 | 规则 | 误判风险 |
|---|---|---|---|
| (1) 域名不存在 | 采用 | 该子项连续 3 次完成的探测都是 `dns_outcome=not_found`（Go `IsNotFound`，NXDOMAIN 或该族无记录） | 本机解析器劫持或分离视图返回 NXDOMAIN 时会误判为目标异常。缓解：见下方“解析器排除” |
| (2) 该族无解析结果 | 采用 | 连续 3 次 `no_address`/`not_found`（例如域名没有 AAAA）；显示“目标异常（无 IPv6/IPv4 解析）” | DNS64 或解析器过滤 AAAA 时会误判。影响小，样本本来就不进分母 |
| (3) 解析到非公网地址 | 采用 | 连续 3 次 `unsafe_address`；字面 IP 的情况保存时就已拒绝 | 几乎确定。唯一例外是使用 `64:ff9b:1::/48` 的 IPv6-only 主机（5.1 节的已知限制） |
| (4) TCP 连续 refused | 不采用 | 照常计入 Connect 失败 | RST 可能来自路径上的设备注入，正是要测的东西；排除它与 M14-C 的“分母是实际的 Connect 尝试次数”冲突 |
| (5) ICMP 长期 0 回包但同地址 TCP 成功 | 不采用 | 照常计入丢包 | ICMP 被限速或屏蔽是路径的属性；排除它与 M14-C 的“用真实的 Echo 发送数和接收数计算”冲突 |
| (6) 超时、SERVFAIL、DNS 超时 | 不采用 | 照常计入 | 无法区分目标故障和路径故障 |

- 计数按次数，不按时间：只看“完成的探测”（`probe_complete`）。第一次出现其他结果就清除“目标异常”。
- **解析器排除**：同一 Agent 上 ≥2 个不同域名在同一窗口（最近 3 次探测）内都 DNS 失败时，这些子项都不标“目标异常”，按普通 DNS 失败显示（很可能是本机解析器的问题）。只有一个域名时无法区分，所以只认 `not_found` 这类明确的应答。不新增“本机 DNS 异常”状态，它不在 R07-6 的列表里。
- `not_found` 是新的 DNS 结果值（现在被归入 `dns_error`），只能经过新协商才发送（4.2 节）。
- 计算位置：Server 根据最近的 staged 样本（`quality_raw.details_json`，保留 8 小时，够用）在读取时计算，作为 `lanes[].condition` 返回。

### 7.4 卡片级文字

- 总开关关闭：“已关闭”。
- 3 个卡槽都没有地址：“未配置目标”。
- 旧 Agent：“需升级 Agent 才能使用自定义目标”。
- 其余按子项状态显示。

## 9. 对 v1.0.6 M14 的影响

- **历史目标**：`SELECT id, payload, created_at, created_revision, retired_at FROM quality_targets WHERE agent_id=?`（包括已退役的），加上 `quality_series`/`quality_buckets` 的存在性和时间范围。
  - payload 里有 `slot, family, protocol, host, port`。按地址分组用 `host/port`。
  - v1.0.4 遗留的 catalog 目标：`source:"catalog"`，标注为“v1.0.4 内置目标”；它们同样按所属卡槽的当前标签显示，payload 里旧的 `region` 不再使用。
- **按地区和 ISP 筛选（A3/A4）——维护者覆盖 T2 后的影响**：
  - 筛选用的地区和 ISP 选项来自 `quality_slot_settings` 的**当前**标签（含自定义值）；每个 target 通过 `slot` 归到卡槽，再取该卡槽的当前标签。等价于“先按卡槽筛选，再把卡槽当前的标签当作它全部历史的标签”。
  - 改标签后，该卡槽全部历史（包括已退役的 target 和 v1.0.4 遗留目标）都会出现在新标签下，并从旧标签下消失。M14 不能按“测量当时的标签”筛选，也不能把“同一地区不同时期标在不同卡槽上的数据”合并。
  - 一台 Agent 只有 3 个卡槽，所以每个标签组合在一台 Agent 上最多对应 3 个卡槽的历史；多线比较（A4）按卡槽比较即可。
  - 地址清空、标签留空的卡槽，历史显示为“卡槽 N（未标注）”，筛选时归入“未标注”。
  - M14 界面要写明：“地区和 ISP 为卡槽当前的用户标注，修改后历史随之改名”。
  - M18 的“按 ISP 评价”同样按当前标签，改标签会改变历史评价的归属；M18 设计时需注意。
  - 如果以后需要“测量当时的标签”，需要新增标签历史表（另一个迁移），不在 v1.0.5 范围内。
- **配置版本**：
  - target 的 `created_revision` 就是它首次生效的配置版本；
  - 历史样本和桶带 `config_revision/slot_revision` 的最小值和最大值（`quality_buckets` 已有），可以按版本区分；
  - `quality_intervals` 在结束后 48 小时就删除，**不能**作为 30 天的版本历史来源。M14 需要更细的“哪段时间是哪个版本”时，用桶里的版本范围加上 target 的 `created_at/retired_at`。如果还不够，在 M14 的设计阶段再提（M14 不在 v1.0.5 的迁移权限内）。
- 现有历史接口（`v3/history`、`v3/card-history`）按 target_id 读取，对已退役的 target 同样可用，R07 不改它们的契约。
- “不改动 M14 详情页的图表”：R07 只改详情页目标下拉的文字，不改图表代码。
