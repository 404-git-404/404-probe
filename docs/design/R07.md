### 1.2 卡槽修订号与配置版本

- `quality_config.revision`：每次“有效保存”加 1。PUT 必须带 `expected_revision`，不相等时返回 `409 revision_conflict`（`ErrQualityConflict`）。如果保存的内容没有变化，直接返回当前配置，版本号不变。
- `quality_slots.revision`（下发给 Agent 时叫 `slot_revision`）：该通道的 target、启用状态或授权最后一次变化时的配置版本。没有变化的通道保留旧值（`qualitySetLaneTx` 第 371 行的跳过逻辑）。
- Agent 上报的每个样本都带 `target_id`、`slot_revision`、`config_revision`。Server 用区间做围栏（`SaveQualityBatch`，`network_quality.go` 第 199–213 行）：必须能找到 `(target_id, slot, family, protocol, revision=slot_revision)` 对应的区间，`config_revision` 在 `[config_from, config_until 或当前版本]` 之内，并且 `started_at` 在 `[start_at−120s, end_at+120s]` 之内，否则 ACK 为 `unauthorized`。这只是围栏部分，完整的接收条件还包括当前会话和能力（`supported`、lane 支持）、样本合法性（`Validate`/`ValidateDetails`、`too_old` 6 小时、`clock_skew`）、去重（`duplicate`/`conflict`）、`history_retired` 和容量（`storage_pressure`）。
- 前端用 `slot_revision` 识别桶是否跨越了配置边界（`cardBlock` 中的 `mixed`），跨越的桶不混合显示。

### 1.3 目标身份

`qualitySetLaneTx` 把 `protocol.QualityTarget{slot,family,protocol,source,region,host,port,endpoint_version}` 和 agent_id 一起做 sha256，取前 32 位十六进制作为 `target_id`。因此：
- 同一 payload 再次出现时复用旧 target，`retired_at` 被清空，历史接上；
- 地区（region）已经包含在指纹里，改地区本来就会产生新目标；
- ICMP 目标的 `port` 固定为 0（`resolveQualityTarget`）。

### 1.4 Server ↔ Agent 协议

- **能力协商**：Agent 每次 `POST /api/v1/report` 都带头 `X-404-Probe-Quality-Version: 2` 和 `X-404-Probe-Quality-Semantics: staged_probe_v2`（`agent.go` 第 545–546 行）。Server 在响应的 `capabilities` 里回 `network_quality`、`network_quality_v2`、`network_quality_staged`（`app.go` 第 282–284 行）。Agent 只有在 Server 回了能力之后，下一次上报才带 `network_quality_v2` 能力 JSON（4 条 lane）。旧 Server 收到无法识别的 v2 内容会返回 400，Agent 退回 v1 后重发一次（`errQualityV2Rejected`）。
- **配置下发**：
  1. 内联：报告被接受后，Server 把当前会话的配置放进报告响应的 `network_quality`（`qualityReportResponse`），整个响应不超过 4096 字节时才放。Agent 默认每 10 秒上报一次（`cmd/agent` 的 `-interval`），所以配置通常在 10 秒内生效。
  2. 拉取：`POST /api/v1/agent/network-quality/config`，请求体 `{version, epoch, session_id}`，响应不超过 16384 字节；最快每 30 秒一次（`nextFetch`），失败时退避。Agent 用 `DisallowUnknownFields` 严格解码。
  3. 配置超过 4096 字节时（例如 12 条通道都填了很长的域名）走拉取，最长约 10 + 30 秒生效。
- **Agent 校验**（`qualityValidateConfig`，`network_quality_http.go`）：slot 只能是 `telecom/unicom/mobile`；v2 的 active 目标必须满足 `Region==RegionID`、`Source=="catalog"`、`Enabled`、IPv6 目标要求 `IPv6==true`、lane capability 支持；间隔 v1 固定 30000，staged 允许 30000–300000 且是 30000 的倍数；jitter 20，超时 5000。只要有一条不合格，整份配置都被拒绝。
- **调度**（`runQualityWorker`）：每条 active 通道按 `interval×(0.8–1.2)` 执行，最多同时 6 个；配置变化时 `reconcile` 取消已经不存在的通道里正在进行的探测。已经测得的样本留在队列里照常上传；只有授权停止（`stopSerial` 变化）才清空队列。
- **上传**：`POST /api/v1/agent/network-quality`，每批最多 64 个样本、8 个缺测；成功后间隔 10 或 30 秒，失败按退避重试。

### 1.5 Agent 端地址检查（unsafe_address）

- `internal/agent/network_quality_guard.go`：`qualityAddressSafe` 先 `Unmap()`，再调用 `protocol.PublicDestinationIP`；`qualityGuardControl` 挂在 `net.Dialer.Control` 上，每次 connect 之前检查实际要连接的地址。
- `internal/agent/network_quality_staged.go`：每次探测都用 `LookupNetIP(ip4|ip6)` 重新解析，取第一个同族结果检查；不安全就记为 `unsafe_address`，不会再找别的地址，然后拨号字面 IP（Control 会再检查一次）。ICMP 同样每次解析并检查，然后直接向检查过的 IP 发包，不经过 TCP 的 `Dialer.Control`。
- 拦截列表（`internal/protocol/public_egress.go`，快照日期 2026-10-15）：
  - 先要求 `IsGlobalUnicast`，带 zone 的拒绝，`Is4In6` 形式拒绝；
  - IPv4 拒绝 `0.0.0.0/8 10/8 100.64/10 127/8 169.254/16 172.16/12 192.0.0/24 192.0.2/24 192.31.196/24 192.52.193/24 192.88.99/24 192.168/16 192.175.48/24 198.18/15 198.51.100/24 203.0.113/24 240/4`（组播和广播在 IsGlobalUnicast 这一步就被拒绝）；
  - IPv6 只允许 `2000::/3`，并拒绝 `2001::/23 2001:db8::/32 2002::/16 2620:4f:8000::/48 3fff::/20`；
  - `PublicDestinationIP` 额外放行 `64:ff9b::/96`（NAT64 知名前缀），按内嵌的 IPv4 判断。
- 版本差异：guard 和 `PublicDestinationIP` 从 v1.0.4 才有。v1.0.2/v1.0.3 的 Agent 也讲 `staged_probe_v2`，但拨号前不检查地址（已用 `git cat-file` 核实）。

### 1.6 ICMP 能力检测

- `detectICMPSocketBackend` 在 Agent 启动时，对每个地址族依次尝试 datagram ICMP（`udp4/udp6`，取决于 `ping_group_range`）和 raw socket（`ip4:icmp/ip6:ipv6-icmp`，需要 CAP_NET_RAW），能打开就算支持。
- `qualityCapabilities()` 上报 4 条 lane：TCP 总是支持；ICMP 按 backend 是否支持；Alpine 被排除时原因写 `platform_excluded`，不支持时写 `unsupported`。
- Server 在保存时不给不支持的 lane 开区间（`qualitySetLaneTx` 的 `active=false`）；读取时把这类通道显示为 `unavailable`。前端 `laneNotice` 显示“不可用（当前环境无 ICMP 权限）”。
- 已知限制：IPv6 ICMP socket 能打开，不代表本机有 IPv6 连通。目前没有任何“本机无 IPv6”的检测。Podman 容器里如果 `ping_group_range` 允许 datagram ICMP，即使没有 CAP_NET_RAW，也会显示“支持”，要在真机上确认（第 10 节）。

### 1.7 容量预算

`qualityBudget.apply`：存储有压力时关闭检测（state `storage_pressure`）；容量不足时把 staged 间隔放大为 `30000×Scale`（state `capacity_throttled`/`retention_degraded`）。

## 2. 数据模型

### 2.1 概念

```
卡片（每台 Agent 一张）
├─ 总开关 enabled                       — 立即生效，按最后一次保存的配置执行
├─ 检测频率 interval_ms                 — 3 个卡槽共用，30000–300000，30000 的倍数，默认 30000
└─ 卡槽 ×3（slot 键固定为 telecom / unicom / mobile，仅作位置编号 1/2/3）
   ├─ 类型 kind：builtin | custom
   ├─ 地区 region、ISP isp              — 用户标注；404-probe 不核对、不校准、不提醒
   ├─ 目标地址 host、TCP 端口 port
   ├─ 卡槽勾选 slot_enabled
   └─ 4 个子项勾选：ipv4_tcp、ipv4_icmp、ipv6_tcp、ipv6_icmp（默认都不勾选）
```

- **slot 键不改名**。`telecom/unicom/mobile` 继续作为位置编号使用（界面显示“卡槽 1/2/3”）。这样 `quality_slots`、`quality_intervals` 的主键、Agent 的 slot 白名单、历史数据都不用动。ISP 不再由 slot 推出，而是来自 `isp` 标签。
- **内置**：`region` 从 31 个省级地区中选（河北 山西 辽宁 吉林 黑龙江 江苏 浙江 安徽 福建 江西 山东 河南 湖北 湖南 广东 海南 四川 贵州 云南 陕西 甘肃 青海 内蒙古 广西 西藏 宁夏 新疆 北京 天津 上海 重庆），`isp` 从 电信/联通/移动 中选。这份列表作为常量写进 `internal/protocol`，不来自 zstatic。存储时保存 `kind=builtin`，同时保存枚举值（省份名、`telecom|unicom|mobile`）。
- **自定义**：`region`、`isp` 都是自由文本（限制见第 6 节）。
- 卡槽已填地址时，地区和 ISP 必填（P17）。
- 类型、地区、ISP 可以随时直接修改，不影响目标身份、不中断曲线（P1，见 2.3 节）。
- **生效条件**（R07-5）：某个子项被执行，当且仅当 卡槽已填地址 ∧ 卡槽已勾选 ∧ 子项已勾选 ∧ 卡片总开关开启 ∧ Agent 支持该子项（能力、族）∧（v6 子项）本机不是“无 IPv6”（7.2 节）∧ Agent 已在当前会话完成协商（4.2 节）∧ 无存储压力、平台未被排除。
- 地址是 IPv4 字面量时 v6 子项不可勾选，是 IPv6 字面量时 v4 子项不可勾选（S5）。域名的 v4 子项只解析 A，v6 子项只解析 AAAA。
- 去掉“V6 检测”（`ipv6` 列不再由用户设置）。卡片上的 IPv4/IPv6 显示切换保留。

### 2.2 存储（迁移 34 新增或修改的部分）

新表，每台设备 3 行：

```sql
CREATE TABLE quality_slot_settings(
  agent_id TEXT NOT NULL REFERENCES agents(id) ON DELETE CASCADE,
  slot TEXT NOT NULL CHECK(slot IN ('telecom','unicom','mobile')),
  kind TEXT NOT NULL CHECK(kind IN ('builtin','custom')),
  region TEXT NOT NULL DEFAULT '' CHECK(length(CAST(region AS BLOB))<=96),
  isp TEXT NOT NULL DEFAULT '' CHECK(length(CAST(isp AS BLOB))<=96),
  host TEXT NOT NULL DEFAULT '' CHECK(length(host)<=253),
  port INTEGER CHECK(port IS NULL OR port BETWEEN 1 AND 65535),
  slot_enabled INTEGER NOT NULL DEFAULT 0 CHECK(slot_enabled IN (0,1)),
  ipv4_tcp INTEGER NOT NULL DEFAULT 0 CHECK(ipv4_tcp IN (0,1)),
  ipv4_icmp INTEGER NOT NULL DEFAULT 0 CHECK(ipv4_icmp IN (0,1)),
  ipv6_tcp INTEGER NOT NULL DEFAULT 0 CHECK(ipv6_tcp IN (0,1)),
  ipv6_icmp INTEGER NOT NULL DEFAULT 0 CHECK(ipv6_icmp IN (0,1)),
  updated_revision INTEGER NOT NULL,
  PRIMARY KEY(agent_id,slot)) WITHOUT ROWID
```

修改：
- `quality_config`：
  - `revision` 沿用，含义明确为**测量版本**：下发给 Agent、写进样本的 `config_revision`、新 target 的 `created_revision`。递增规则见 2.4 节的规则表（D1）。
  - 新增 `settings_revision INTEGER NOT NULL DEFAULT 0`（迁移时先以默认值加列，再回填为新版本号）：**设置版本**，作为 Web 的乐观锁（`expected_revision` 和它比较）。递增规则见 2.4 节。
  - 新增 `interval_ms INTEGER NOT NULL DEFAULT 30000 CHECK(interval_ms BETWEEN 30000 AND 300000 AND interval_ms%30000=0)`。
  - 新增 `targets_granted INTEGER NOT NULL DEFAULT 0 CHECK(targets_granted IN (0,1))` 和 `capability_snapshot TEXT`（JSON，长度上限 2048）：设备级的“最后一次确定的协商结果和 lane 能力”，授权重算只读这两列（4.3 节）。
  - `ipv6`、`choices`、`region_id`、`v2_lanes` 成为遗留列：迁移时写成中性值（`ipv6=0`、默认 choices、`region_id=''`、`v2_lanes=NULL`），新代码不再读取。
- `quality_capability`（当前会话一行）新增 `user_targets INTEGER NOT NULL DEFAULT 0 CHECK(user_targets IN (0,1))` 和 `ipv6_address TEXT NOT NULL DEFAULT 'unknown' CHECK(ipv6_address IN ('present','none','unknown'))`（4.2 节）。
- `quality_targets` 新增 `identity TEXT`（地址身份，见 2.3，不含标签）、`created_revision INTEGER`（**创建时的测量版本**，不等于首次生效的版本）和 `first_active_at INTEGER`（第一次开区间的时间；区间 48 小时后会被删除，所以单独记下）。旧行为 NULL。新 target 的 `payload` 不含标签键。
- 标签（类型、地区、ISP）只存在 `quality_slot_settings`，不另建标签历史表（P1）。
- 12 条通道仍由 `quality_slots`/`quality_intervals` 表示，每个卡槽 4 条（family×protocol），与现在相同。
- `quality_slots.target_id` 的含义改为“该通道当前的目标”：卡槽填了地址就指向当前 target，**不论通道是否开放**（总开关关闭、未勾选时也保留）；卡槽地址为空时为 NULL。`quality_slots.enabled` = 卡槽勾选 ∧ 子项勾选。这样关闭状态下改地址也能按 2.3 节判断是否新建目标。

### 2.3 目标的身份和版本（R07-7；release-decider T1；**维护者决定覆盖 T2**）

- **维护者决定覆盖 T2**（P1）：目标身份只由地址、端口（仅 TCP）、协议族决定。地区、ISP 标签和卡槽类型（内置/自定义）改了不算新目标，可以直接修改，曲线不中断，历史一律按当前标签显示。release-decider 原结论（T2 选 B：标签进入指纹）不再采用。
- **身份键** `identity = sha256(agent_id, slot, family, protocol, host 的规范形式, tcp ? port : 0)`。
  - 本文把“协议族”理解为通道本身的地址族（IPv4/IPv6）和协议（TCP/ICMP）；`slot` 也在键里，因为每个通道属于一个卡槽，不同卡槽填同一地址仍是不同的目标。
  - `kind`、`region`、`isp` **不在键里**。与 v1.0.4 现状（region 在指纹里）不同。
  - ICMP 子项的身份不含端口，所以只改 TCP 端口不会拆开 ICMP 的历史（T1 条件 2）。
- **地址每变一次都新建**（T1 选 B，不变）：`target_id = sha256(identity, created_revision)` 的前 32 位十六进制，`fingerprint` 列存同一个值（满足现有的 `UNIQUE(agent_id,fingerprint)`）。改成 B 再改回 A 时也新建 target，不接回旧历史，卡片曲线不会把切换前的 A 段接回来。
- **不新建的情况**：保存时某个通道新算出的 `identity` 等于其当前 target 的 `identity`，就保留原 target。只改标签、只改类型、只改开关、改频率、取消再勾选子项、总开关变化、能力变化都属于这种情况。
- **标签只存一份，在 `quality_slot_settings`**。target 的 `payload` 只保存 Agent 需要的字段（`slot,family,protocol,source:"user",host,port`），不含任何标签键。Web 读模型显示任何 target（当前的或已退役的）时，都按它的 `slot` 取该卡槽**当前的**类型、地区、ISP。
- **只改标签或类型的保存**（release-decider D1 选 A：拆成两个版本号）：
  - `settings_revision` +1（乐观锁，其他标签页靠它发现变化）；
  - **测量版本 `revision` 不变**，target、区间、`slot_revision` 都不变；下发给 Agent 的配置完全不变。
  - 因为样本的 `config_revision` 不变，现有的 5 分钟 P50（`network_quality_rollup.go` 的 `qualityFiveMinuteP50`）、TCP Mini 证据（`tcp_mini.go` 中跨 `config_revision` 的分钟被跳过）、前端 `cardBlock`/`latency-mini` 的边界判断都**不需要修改**，曲线和 12 格自然连续。第 2 版 8.3 节“前端不再比较 `config_revision`”的计划撤回。
  - 地址、频率、勾选、总开关的变化会改变测量版本（2.4 节），跨这些变化的分钟仍按现有规则作为边界（这些变化确实改变了测量）。
- 配额：每设备 512 个 target 不变。每次改地址最多新建 4 个，大约允许 30 天内改 128 次。只改标签不消耗配额。没有被引用的 target 在历史桶过期后由现有清理逻辑删除（`network_quality_retention.go` 第 94 行）。配额用尽时保存返回 `409 quality_quota`，并要有测试。
- **这样做的影响**：
  - **标签修改不留历史**：数据库里只保存当前标签。无法回答“这个卡槽上周标的是哪个地区”，也无法还原某段数据测量时的标签。
  - **历史随标签一起改名**：把卡槽 1 从“广东 电信”改成“上海 联通”后，卡槽 1 的全部历史（包括它以前填过的地址对应的已退役 target，以及 v1.0.4 遗留的内置目标历史）都按“上海 联通”显示。
  - 卡槽地址清空后标签可以留空（P17 只要求已填地址时必填）；这时该卡槽的历史按“卡槽 N（未标注）”显示。
  - 对 M14 的影响见第 9 节。

### 2.4 两个版本号的递增规则（复核 R1）

一次保存、一次总开关请求、一次授权重算，都在**一个事务**里按以下顺序处理：

1. 比较 `expected_revision` 与 `settings_revision`（只对 Web 请求；授权重算没有这一步）。
2. 把新设置规范化（地址规范形式、端口、勾选、频率、总开关），与已存设置比较，得到两个判断：
   - `settingsChanged`：任何字段变化（包括标签和类型）；
   - `measurementChanged`：除标签和类型以外的任何字段变化，即任何卡槽的地址、TCP 端口、卡槽勾选、子项勾选，总开关，频率。
3. 按新设置、授权快照和能力，算出“应开放的授权描述”：集合元素是 `(slot, family, protocol, target_identity)`，**包含目标身份**，不只是通道键。与当前开放区间（及其 target 的 identity）比较，得到 `authorizationChanged`。
4. 若 `measurementChanged ∨ authorizationChanged`：**预分配一次** `newRevision = revision + 1`；否则 `newRevision = revision`，测量版本不变。一次事务最多 +1，不论改了多少条通道。
5. 对每条通道：新的 identity 与 `quality_slots.target_id` 所指 target 的 identity 不同（含从空变为有地址），就新建 target，`created_revision = newRevision`，并把 `quality_slots.target_id` 指向它；地址变为空则置 NULL。因为第 4 步已经分配了新版本，同一事务里新建的 target 一定使用新版本号，关闭状态下 A→B→A 也会得到三个不同的 target_id。
6. 区间差分（按第 3 步的授权描述）：
   - 描述中消失的（含同一通道换了 target 的旧 target）：关闭区间，`end_at = now`、`config_until = revision`（旧值）；
   - 新出现的（含同一通道的新 target）：开区间，`revision = config_from = newRevision`，第一次开时写 target 的 `first_active_at`；
   - 没有变化的开放区间保持不动（`config_until` 仍为空，后续样本的新版本号仍落在区间内）。
7. `quality_slots.revision`（`slot_revision`）：只对 target、`enabled` 或开放状态发生变化的通道设为 `newRevision`，其他通道不变。
8. `settings_revision`：Web 请求且 `settingsChanged` 时 +1（一次事务最多 +1）；授权重算不改它。
9. 写回 `revision = newRevision`。

规则表：

| 变化 | `settings_revision` | 测量 `revision` | target | 区间 | `slot_revision` |
|---|---|---|---|---|---|
| 只改标签或类型 | +1 | 不变 | 不变 | 不变 | 不变 |
| 改地址或 TCP 端口，总开关**开启** | +1 | +1 | 受影响通道新建（`created_revision` = 新版本） | 受影响的开放通道：关旧 target 区间、开新 target 区间 | 受影响通道 = 新版本 |
| 改地址或 TCP 端口，总开关**关闭** | +1 | +1 | 受影响通道新建（同上） | 不变（本来就没有开放区间） | 受影响通道 = 新版本 |
| 改卡槽勾选或子项勾选 | +1 | +1 | 不变 | 按需开或关 | 受影响通道 = 新版本 |
| 只改频率（开启或关闭） | +1 | +1 | 不变 | 不变（开放区间继续） | 不变 |
| 总开关变化，有可执行的通道 | +1 | +1 | 不变 | 全部开或全部关 | 受影响通道 = 新版本 |
| 总开关变化，没有可执行的通道 | +1 | +1（Agent 收到的 `enabled` 变了） | 不变 | 不变 | 不变 |
| 授权重算使开放集合变化（协商、ICMP 能力、本机无 IPv6） | 不变 | +1 | 不变 | 按需开或关 | 受影响通道 = 新版本 |
| 授权重算没有变化 | 不变 | 不变 | — | — | — |
| 内容完全相同的保存、总开关 no-op（4.1 节） | 不变 | 不变 | — | — | — |
| 一次保存同时改多项 | 最多 +1 | 最多 +1 | 按各通道规则 | 按各通道规则 | 按各通道规则 |

不变量（阶段 B 的测试逐条断言）：
- 每条通道的 `slot_revision` ≤ 测量 `revision`；每个 target 的 `created_revision` ≤ `revision`；
- 每个开放区间 `config_from` = 该通道的 `slot_revision`，`config_until` 为空；同一通道上，已结束区间的 `config_until` < 下一个区间的 `config_from`；
- Agent 收到的配置 `revision` 等于数据库里的测量 `revision`，样本的 `config_revision` 落在对应区间内；
- 只改标签或类型时，Agent 收到的配置逐字节不变。

## 3. 迁移 34

### 3.0 编号

- 维护者分配：迁移 33 归 R23（YouTube 送中状态，由另一个会话施工），R07 的迁移从 34 开始编号。两者都由 Claude Code 施工，仍然满足“同一版本只由一方新增迁移”。
- 依赖：`migrate()` 按版本号顺序执行 `if version < N`，所以迁移 34 必须排在 R23 的迁移 33 之后，`currentSchemaVersion` 最终为 34。
- 维护者决定（P18）：R23 的迁移 33 先合入，阶段 B 在它之上开发。`claude/v1.0.5` 上已有 R23 的迁移 33（`internal/storage/google_status_migration33.go`，`currentSchemaVersion = 33`，提交 `047898701`），阶段 B 以此为基准。
- 迁移 34 只操作网络质量的表，不依赖、也不修改迁移 33 的内容。

### 3.1 内容（单事务；评审 M5）

迁移分四层执行（第 0–3 层），每层的范围和不变量如下。`now` 在迁移开始时取一次。

**第 0 层：结构**
- 创建 `quality_slot_settings`；给 `quality_config` 加 `settings_revision`、`interval_ms`、`targets_granted`、`capability_snapshot`；给 `quality_capability` 加 `user_targets`、`ipv6_address`；给 `quality_targets` 加 `identity`、`created_revision`、`first_active_at`。

**第 1 层：每台设备一次**
- 遍历范围：所有 `quality_config` 行，加上“有 `quality_slots` 行或开放区间、但没有 `quality_config` 行”的 Agent（防御性情况：为它补一行 `quality_config`，旧版本 `rev` 取其 `quality_slots.revision` 与 `quality_intervals.revision` 的最大值）。
- 每台设备只读一次旧版本 `rev`，统一写成：
  - `revision = rev+1`，`settings_revision = rev+1`；
  - `enabled = 0`（维护者决定 P3，无论原来是否有目标都执行，包括“无目标但 enabled=1”的配置）；
  - `interval_ms = 30000`，`targets_granted = 0`，`capability_snapshot = NULL`；
  - 遗留列写成中性值。
- 生成 3 行 `quality_slot_settings`（R07-8）：
  - `kind='builtin'`，`host=''`，`port=NULL`，卡槽和 4 个子项全部不勾选，`updated_revision = rev+1`；
  - `isp` 由 slot 推出（telecom→电信 等，存枚举值）；
  - `region` 由 v1.0.4 的地区推出：先取 `region_id`，为空就取该 slot 在 choices/v2_lanes 里的 `region`。省级 id `["province","河北",null]` 取省名；城市 id `["city","广东","深圳"]` 取所属省份（广东，维护者决定 P2）。省名不在 31 个省级地区常量里、未选择、或 JSON 无法解析的，一律留空，并记一条 Warn（不中断迁移）。不使用已删除的目录做查询，只解析 id 本身。
  - 标签只写进 `quality_slot_settings`。v1.0.4 遗留 target 的 payload 保持原样不改。

**第 2 层：每条通道**
- 只对开放区间（`end_at IS NULL`）写 `end_at = now`、`config_until = rev`；已经结束的区间保持原值，一行都不改。
- 所有 `quality_slots` 行：`target_id = NULL`、`enabled = 0`、`revision = rev+1`（每台设备同一个值，不按通道累加）。

**第 3 层：目标**
- `UPDATE quality_targets SET retired_at = now WHERE retired_at IS NULL`：经过第 2 层后，已经没有任何 slot 引用旧目标。这条语句不解析 payload，所以 payload 损坏的 target 也一样处理；已有的 `retired_at` 保持原值。
- 样本、桶、序列、TCP Mini 状态都不删，历史全部保留。

**校验与登记**
- `quality_usage` 与 `quality_totals` 的区间计数一致，`PRAGMA foreign_key_check` 没有违规（照搬迁移 26）；没有 `end_at IS NULL` 的区间；每个 `quality_config` 行都有 3 行设置。
- 写入 `schema_migrations(34)`，`currentSchemaVersion = 34`。

**失败与重试**
- 整个 `migrate()` 是一个事务（33 和 34 在同一个事务里）。因此：从 32 升级时迁移 34 失败，数据库回到 32（迁移 33 也一起回滚）；从 33 升级时失败，仍为 33。再次启动会从头重试，因为前一次什么都没提交，版本号不会被重复增加。

### 3.2 可回滚性（release-decider T7：认可）

区分三种情况：
1. **迁移本身失败**：事务自动回滚（3.1 节），Server 不会以半迁移状态运行，旧数据不变。
2. **升级安装失败**（例如新服务起不来）：按安装器现有的升级事务恢复（`install.sh` 的 `SERVER_UPGRADE_BACKUP`，含 db/WAL/SHM、二进制、配置和单元文件）。
3. **升级成功后想退回 v1.0.4**：不提供降级迁移。v1.0.4 二进制遇到 schema 34 会拒绝启动（`checkSupportedSchemaVersion`）。办法是停止服务，用 v1.0.4 二进制和升级前的备份一起手工恢复，升级后产生的数据会丢失。备份只保留最近两次（`backup`、`backup.previous`），再升级两次后这个回滚点就没有了。README 已有“Do not downgrade a migrated database”的先例。

- 阶段 E 在测试 Server 上实际演练一次手工恢复，验证内容包括：备份清单和 SHA256SUMS、WAL/SHM、配置和单元文件，以及恢复后 Server 能读取历史数据，不只验证能启动。
- v1.0.5 Agent 连回 v1.0.4 Server 必须正常工作（第 4.4 节），因为 Agent 没有降级路径。

## 4. API 与 Agent 协议

### 4.1 Web API（新增 v4，旧的写接口移除）

| 方法和路径 | 说明 |
|---|---|
| `GET …/network-quality/v4/config` | 读取：`settings_revision, config_revision, enabled, interval_ms, effective_interval_ms, state, agent_support, slots[3], lanes[12]` |
| `PUT …/network-quality/v4/config` | 保存：`{expected_revision, interval_ms, slots[3]}`；**不含 enabled，保存不改变总开关** |
| `PUT …/network-quality/v4/enabled` | 总开关：`{expected_revision, enabled}` |

- 版本字段（D1）：`settings_revision` 用于 `expected_revision`；`config_revision` 是测量版本，前端用它比较样本和作为缓存键。不再有含义不清的 `revision` 字段。
- `slots[i] = {slot, kind, region, isp, host, port, slot_enabled, ipv4_tcp, ipv4_icmp, ipv6_tcp, ipv6_icmp}`。请求必须正好 3 个且 slot 不重复；严格解码，未知字段返回 400。
- `lanes[j] = {slot, family, protocol, target_id|null, slot_revision, status, condition}`。`status`/`condition` 见第 7 节，由 Server 计算，前端不自行推断。
- `agent_support`：`user_targets`（当前会话已协商）、`negotiating`（新会话尚未完成第二步）、`upgrade_required`（旧 Agent）、`unsupported`（无网络质量能力）、`excluded`（平台排除）。
- 请求体上限 16384 字节；超过时返回 413，不解码。
- **保存**：
  - 在事务外先做原始请求体检查（第 6 节）、输入校验（第 5、6 节）和 Server 侧解析（5.2 节）；
  - 然后在事务内比较 `expected_revision` 与 `settings_revision`；
  - 之后按 2.4 节的顺序在同一事务里处理：判断变化、预分配一次新测量版本、新建 target、区间差分、更新 `slot_revision` 和两个版本号；
  - 内容完全没变化时什么都不改，返回当前配置；
  - 只改标签或类型：只有 `settings_revision` +1（2.4 节规则表）。
  - 总开关已经开启时，保存的新配置立即生效（“按最后一次保存的配置执行”）；总开关关闭时，只保存，不开区间。
  - 频率：30–300 秒，每档 30 秒（维护者决定 P10），其他值返回 `invalid_interval`。
- **总开关**（release-decider T4 + D7）：
  - 开启（false→true）：必须带 `expected_revision`，不一致返回 `409 revision_conflict`。开启等于“执行最后一次保存的配置”，必须是用户看到过的那一版。
  - 关闭（true→false）：不校验版本，总是成功（最后写入者胜）。关闭是安全的方向，被冲突挡下的话探测会违背用户意图继续运行。
  - 幂等请求（D7）：false→false 总是 200、不改任何东西；true→true 且版本一致时是 no-op；true→true 但版本过期返回 409（保持 T4“开启必须是看过的版本”）。no-op 不改版本号、不动区间，返回当前配置。
  - 状态真正变化时：按 2.4 节处理（`settings_revision` +1，测量版本 +1，按需开关区间），返回最新配置。
  - 请求只接受 `enabled` 和 `expected_revision`。
- **并发冲突**：沿用乐观锁，比较对象是 `settings_revision`。
  - 前端收到 409，或者总开关响应里的配置内容与草稿基准不一致时，要把服务器的最新内容一起换成新基准，并提示“配置已被修改”。不能只换版本号，否则下一次保存会悄悄覆盖另一方的改动（T4 条件 2）。
  - 弹窗自己执行的总开关操作成功后，如果返回的卡槽内容与基准相同，只更新基准版本号，草稿保留。
- **错误**：`400 invalid_request` 带字段级 `details[]`，例如 `{slot:"unicom", field:"host", code:"unsafe_address"}`（错误码 `invalid_host`、`reserved_name`、`unsafe_address`、`family_mismatch`、`invalid_port`、`invalid_label`、`label_required`、`invalid_interval`、`invalid_encoding`），供界面标注到对应的输入框。错误响应**不回显**解析出的 IP 或 DNS 细节。`409 quality_quota`、`409 unsupported`、`503 storage_pressure` 沿用；DNS 检查并发已满时返回 `503 retryable`。
- **移除和旧页面**：
  - 移除 `GET /api/v1/web/network-quality/catalog`、`GET/PUT …/config`、`GET/PUT …/v2/config`、`GET …/v3/card-config`。
  - 静态文件嵌入二进制，但 Server 升级时已经打开的旧页面不会自动刷新（评审建议 6）。所以这些旧路由不直接 404，而是统一返回 `410`，JSON `{error:{code:"client_outdated", message:"页面版本已过期，请刷新页面后重试"}}`。旧页面的保存会显示“未确认保存成功：页面版本已过期，请刷新页面后重试”，不会静默失败；阶段 D 用 v1.0.4 的前端代码验证这条提示。
- **保留**：`v3/card-history`、`v3/history`、`v3/tcp-mini`、`history`、`v2/history`。它们都按 target_id 读取，已退役目标的历史照常可读（`network_quality_history.go` 第 74–92 行只要求 target 属于该 Agent）。返回的 `target` 由 Server 补上卡槽当前标签。

### 4.2 Agent 协议：两步协商（release-decider S1 选 A；评审 M3；release-decider D3）

**原则**：只有在**当前会话**里完成两步协商的 Agent 才会收到自定义目标。请求头和能力字段都是 Agent 自报的，只能用来区分“新版正常 Agent”和“旧版 Agent”，不能证明二进制版本，也不是对恶意 Agent 的远程证明（恶意 Agent 本来就能自己拨号）。安全边界仍是新 Agent 每次连接前的地址检查。

**线上格式示例**（新 Agent 刚启动，新会话 `epoch=E`、`session_id=S`）：

1. 第一次上报：`POST /api/v1/report`，带头 `X-404-Probe-Quality-Version: 2`、`X-404-Probe-Quality-Semantics: staged_probe_v2`、**`X-404-Probe-Quality-Targets: user_v1`**；请求体 `network_quality:true`，没有 `network_quality_v2`（Agent 重启后 `qualityV2Supported` 为 false）。
   - Server：`saveQualityCapabilityTx` 写当前会话行，`user_targets=0`（第一步不授权）。
   - 响应：`capabilities` 含 `network_quality, network_quality_v2, network_quality_staged`，并且因为带了头，含 **`network_quality_user_targets: true`**。内联配置用旧格式（下面第 5 点）。
2. 第二次上报：同样带头；请求体的 `network_quality_v2` 是完整能力 JSON，新增字段 **`"targets":"user_v1"`** 和 **`"ipv6_address":"present|none|unknown"`**（只有收到第一步的能力后才发送）。
   - Server：`QualityCapabilities.Validate` 只接受 `targets` 为空或 `user_v1`；`ipv6_address` 只在 `targets=user_v1` 时允许出现。`saveQualityCapabilityTx` 写 `user_targets = (带头 && targets=="user_v1")`、`ipv6_address`。
   - 资源报告事务提交后，在单独的事务里执行授权重算（4.3 节），失败只记日志，不影响资源 ACK（现有 `qualityReportResponse` 的位置）。
   - 响应：内联新格式配置（含自定义目标，`source:"user"`）。
3. 配置拉取：`POST …/network-quality/config`，带同一个头，请求体 `{version, epoch:E, session_id:S}`。
   - Server：请求体的 epoch/session_id 必须与 `agent_state` 一致（现有检查），并且该会话行 `user_targets=1`、本次请求带头，才发新格式；否则发旧格式。
4. 上传样本：`SaveQualityBatch` 对 `source:"user"` 的目标，额外要求当前会话行 `user_targets=1`（D3 修正 3），否则 ACK `unauthorized`。
5. **旧格式**（发给未授权的会话，包括旧 Agent；D3 修正 2）：
   - `version` 与请求一致；`revision` = 当前测量版本（不能是 0 或更小，否则旧 Agent 的 `install` 会因 next<old 拒绝，继续运行原来的 catalog 配置）；
   - `supported: true`（否则内联路径不附带配置）；`enabled: false`；`ipv6: false`；`targets: []`；
   - `interval_ms: 30000`、`jitter_percent: 20`、`timeout_ms: 5000`，`semantics` 与会话一致；v2 时 `state: "agent_upgrade_required"`，`region_id` 为空；
   - **不带 `capabilities` 字段**，避免旧版 `QualityCapabilities.Validate` 因未知的 lane 原因拒绝整份配置；
   - 不含任何用户目标的 host/port/id。
   - 阶段 B 必须用 v1.0.2、v1.0.3、v1.0.4 的 `qualityValidateConfig` 和 `install()` 实际验证：接受这份配置，并且停止所有通道。

**撤销与变化**：
- 会话更换（Agent 重启、epoch/session 变化）：新会话行从 `user_targets=0` 开始，必须重新走两步；旧会话的请求因 epoch/session 与 `agent_state` 不一致而被拒绝（现有检查）。
- 上报不带头：会话行 `user_targets=0`；这是“撤销”证据（4.3 节）。
- 带头但没有 `targets` 字段，或者没有 v2 能力：会话行 `user_targets=0`，但对设备级授权来说是“未知”，不触发重算（避免每次重启都关区间再开区间）。
- 中间层给所有请求统一加头：旧 Agent 不会发送第二步的 `targets` 字段，所以永远得不到授权。
- Agent 侧：上报响应中 `network_quality_user_targets` 从 true 变成 false，或报告因新字段被旧 Server 返回 400（扩展现有的 `errQualityV2Rejected` 降级），Agent 立即调用 `stopQuality` 清除缓存的配置和在途探测，并清除协商状态，之后按旧协议运行。
- 新 Agent 的校验：已协商时接受 `source=="user"`，不检查 region；收到目标后用与 Server 相同的规则（`internal/protocol`）重新校验主机名，并照旧做每次连接前的公网检查。未协商时（连 v1.0.4 Server）保持 v1.0.4 的 catalog 校验路径。
- 协商之后才发送的新内容：`targets`、`ipv6_address`（D4）、staged details 的 `dns_outcome:"not_found"` 和 `error_code:"not_found"`（7.3 节）。旧 Server 不会回能力，新 Agent 也就不会发给它。
- **资源上报的隔离**：`Report.Validate` 会校验 `network_quality_v2`，能力保存失败会回滚整个资源报告事务，这是现有的耦合。缓解办法：新字段只在协商后发送；Server 对新字段的校验只做枚举检查；授权重算、DNS、目标异常计算都放在资源事务之外；Agent 遇到 400 时用现有的“去掉 v2 再发一次”降级。测试要断言资源报告被 ACK、计数连续。

### 4.3 授权重算（评审 M3；release-decider D3 修正 1）

- 函数 `qualityReconcileAuthorizationTx(agent, now)`：由“设置 + 总开关 + 频率 + 设备级授权快照（`targets_granted`、`capability_snapshot`）+ 平台排除 + 存储压力”算出应该开放的通道集合，与当前开放区间做差：
  - 比较的对象是包含目标身份的授权描述 `(slot, family, protocol, target_identity)`，同一通道换了 target 也算变化；
  - 区间的关和开、`slot_revision`、测量版本的预分配和递增，完全按 2.4 节的第 3–7、9 步；
  - **没有变化时什么都不写**（no-op）。保存和总开关请求也走同一个函数，只是多了 2.4 节第 1、2、5、8 步。
- 设备级快照只在有**确定证据**时更新（三态）：
  - 带头 + 完整 v2 能力 + `targets=user_v1` → 授予：`targets_granted=1`，`capability_snapshot` = 本次能力（lane 支持、`ipv6_address`）；
  - 不带头的上报 → 撤销：`targets_granted=0`；
  - 其他情况（带头但缺 `targets`、没有 v2 能力，例如重启后的第一次上报）→ 未知：快照不变，不触发重算。
  - lane 能力（ICMP、本机无 IPv6）只在报告带完整 v2 能力时更新。
- 调用时机：保存、总开关变化、授予/撤销/能力变化的上报之后（单独事务）。**配置拉取不调用**（拉取不带能力，也不应该写库）。
- 效果：
  - 旧 Agent 升级到新版后，第二次上报完成协商，已保存且开启的配置自动开始执行；
  - `ipv6_address` 从 `none` 变 `present` 时，v6 通道自动重新开放（新 `slot_revision`，target 不变，历史有缺口但不断开身份）；
  - ICMP 能力在 Agent 重启后变化时，ICMP 通道自动关或开。
- 未授权会话期间（重启后约一个上报周期）设备级区间保持不变；这段时间 Server 只给该会话发旧格式配置，所以 Agent 不会执行；样本上传被第 4 点的会话门控拒绝。

### 4.4 兼容矩阵

| 组合 | 行为 |
|---|---|
| 旧 Server（v1.0.4）+ 旧 Agent | 不变 |
| 旧 Server + 新 Agent | 头被忽略，没有新能力，Agent 不发送新字段；按 v1.0.4 运行（catalog 目标、30 秒）。必测 |
| 新 Server + 旧 Agent（v1.0.2–v1.0.4） | 只收到旧格式配置（4.2 第 5 点），停止所有通道；卡片显示“需升级 Agent”；CPU、内存、流量上报不受影响（要实测资源 ACK） |
| 新 Server + 新 Agent | 全部功能 |

### 4.5 关闭、生效与补传的时限（评审 M7；release-decider T3）

分四件事说明。所有时间都以“默认上报周期 10 秒、网络正常、请求成功”为前提，**这些都不是硬性保证**。

1. **Server 授权何时关闭**：保存或总开关变化的事务提交时，区间立即关闭（`end_at` = 提交时间）。
2. **Agent 正常链路何时停止调度**：下一次被接受的上报带回内联配置时停止（默认约 10 秒；上报周期可以用 `-interval` 调整）。配置超过 4096 字节时要等配置拉取（至少 30 秒节流），拉取失败会退避，最长 5 分钟。阶段 C 的可选改进：Server 在上报响应里附带当前测量版本号（旧 Agent 宽松解码，不受影响），新 Agent 发现版本更新但没有内联配置时立即拉取，不等 30 秒节流。
3. **通信故障时**：没有配置租期（维护者决定不设，作为已知行为）。Agent 收不到新配置时会继续按最后一份配置检测，直到收到新配置，或者收到 401/403/404/unsupported 失去授权。Server 离线升级期间同样如此：旧 Agent 会按内存中的 catalog 配置继续检测，直到 Server 恢复后它收到第一份有效的旧格式停用配置。迁移完成本身不能让离线的 Agent 停止。
4. **授权期内测得的样本怎么补传、何时过期**：
   - Agent 队列最多保留 6 小时、6000 行、2 MiB（`network_quality_queue.go`），关闭配置不会清空队列；上传失败按退避重试，最长 5 分钟一次。
   - Server 接收时仍要满足全部条件（1.2 节）：样本的 `config_revision` 在区间的 `[config_from, config_until]` 内，`started_at ≤ end_at + 120s`（这是**样本开始时间**的时钟容差，不是上传截止时间），会话、能力、`too_old`（6 小时）、去重和容量。
   - 因此：关闭前测得的样本，在正常链路下随后几十秒内补传；通信故障时在恢复连接后补传，只要不超过 6 小时。关闭之后才开始的样本，只有 `started_at` 落在 `end_at+120s` 之内的会被接受（Agent 还没收到停用配置时测得的），其余 ACK `unauthorized`，被 Agent 永久丢弃。
   - 维护者的 P6 结论（“关闭后不再产生新的测量，关闭前已测得的样本照常补传”）语义不变；第 2 版写的“最多约 40 秒”只适用于正常链路，第 3 版更正为上面的说法。
- **已知行为**（维护者决定接受，不设配置租期）：关闭没有硬性的停止期限。Agent 与 Server 通信中断时，会按最后一份配置继续检测，直到重新收到配置或失去授权。发布说明中写明。
- 升级时迁移 34 结束所有内置线路（`end_at` = 迁移时间）。旧 Agent 在 Server 离线期间测得的 catalog 样本：迁移时间之前开始的，在 6 小时内补传仍被接受；之后开始的超过 `end_at+120s` 就被拒绝。不会写入新目标。
- **Server 升级到 v1.0.5 之后，所有 Agent 的网络质量检测都会停止，直到用户填写目标（旧 Agent 还要先升级）。** 这是 R07-1 和 S1 的直接后果。维护者已知悉，发布说明中写明（P5）。
- CPU、内存、流量上报与网络质量的开关分开，但这一点要靠 4.2 节的隔离措施和兼容测试来证明，不能只凭职责分层推出。

## 5. 地址安全

### 5.1 拦截列表（release-decider S4：维持现状，继续共用；NAT64 按维护者决定 N1 选 B）

继续以 `protocol.PublicDestinationIP` 作为唯一的判断点（与公网出口检查共用 `egressDenied`），v1.0.5 不扩充普通拦截列表，也不另建网络质量专用列表。
- **IPv4**：见 1.5 节，另有 IsGlobalUnicast 拒绝的组播、广播、未指定、回环。
- **IPv6**：只允许 `2000::/3`，拒绝 Teredo/ORCHID（`2001::/23`）、文档地址（`2001:db8::/32`、`3fff::/20`）、6to4（`2002::/16`）、AS112（`2620:4f:8000::/48`）；ULA `fc00::/7`、链路本地、组播、`::`、`::1` 都不在 2000::/3 之内。
- **IPv4 映射**（`::ffff:a.b.c.d`）：保存时转成 IPv4 字面量，归入 v4 族，按 IPv4 判断（S3）。拨号检查先 `Unmap` 再判断，这一点保留。DNS 返回的映射地址不会被当作 IPv6（v6 子项结果为 no_address，这是正确的：那条路径根本不是 IPv6 连通性）。
- **NAT64（评审 M4；维护者决定 N1 选 B）**：
  - 知名前缀 `64:ff9b::/96`：按内嵌 IPv4 判断（现状，Server 保存时和 Agent 连接前都检查）。本地用途前缀 `64:ff9b:1::/48`（RFC 8215）不在 2000::/3 内，一律拒绝（现状）。
  - **网络特定前缀：Agent 按 RFC 7050 自动发现**（阶段 C 实现，无配置界面）：
    - 通过系统解析器查询 `ipv4only.arpa` 的 AAAA；
    - 在每个返回地址里，按 RFC 6052 的六种前缀长度查找知名地址 192.0.0.170 或 192.0.0.171，找到的位置就给出一个前缀和长度；一个网络可能有多个前缀，都保留（去重，最多保留 8 个）。各长度的布局（复核 R2 改正）：
      - /32、/40、/48、/56、/64：第 64–71 位是 u 字节，**不属于前缀也不属于 IPv4**，提取时跳过；u 字节必须为 0，否则该长度的候选不成立；
      - **/96：前 96 位全部属于前缀，第 64–71 位是前缀的一部分，可以是任意值，不检查 u 字节**；IPv4 是最后 32 位；
      - 第 5 版之前写的“六种长度都含 u 字节、u 必须为 0”是错误的，会把第 64–71 位不为 0 的合法 /96 前缀排除在外；
    - Agent 启动时查询一次，之后每 10 分钟刷新，失败按退避重试、最长 1 小时（现有解析接口不返回 TTL，所以这是有上下限的固定刷新，不是严格遵守 TTL，见 11.1 节 G6）；查询失败时保留上一次发现的结果；没有 AAAA 表示没有发现 DNS64；
    - **判定规则是在原有检查之外再附加一层 AND**（复核 R2），不是替换原有检查：

      ```
      allow(addr) =
          原有检查允许 addr            // PublicDestinationIP（含 Unmap、族、zone、2000::/3、拦截列表、64:ff9b::/96 特例）
          AND 对每一个包含 addr 的发现前缀 P:
                按 P 的长度用 RFC 6052 布局取出内嵌 IPv4 成功（/32–/64 要求 u 字节为 0）
                AND PublicEgressIP(内嵌 IPv4, "ipv4")
      ```
      - 原有检查拒绝的地址，不会因为落在某个发现前缀内、内嵌公网 IPv4 而变成允许（例如落在 `2001:db8::/32` 的地址仍然拒绝）；`64:ff9b::/96` 的处理仍由原有检查决定，不新增任何例外；
      - 多个发现前缀重叠时，**所有**包含该地址的前缀都要通过，任何一个取不出或内嵌私网 IPv4 就拒绝，结果记 `unsafe_address`；
      - 因此对同一个地址，增加发现结果只可能把“允许”变成“拒绝”，不可能反过来；解析器返回伪造的前缀，最坏只是多拦截一些地址；
    - Server 不知道 Agent 所在网络的前缀，保存时只能检查知名前缀；发现到的前缀不上报给 Server。
  - **已知限制**（维护者决定写进文档，并在阶段 E 的发布说明中注明）：
    - 没有 DNS64、无法通过 `ipv4only.arpa` 发现的 NAT64（例如只通过 RA PREF64 通告前缀，或手工配置的转换器），其网络特定前缀不会被识别，内嵌的私网 IPv4 按普通全局 IPv6 放行；
    - 发现失败或尚未完成（例如 Agent 刚启动、解析器故障且之前从未成功）时，同上；
    - 只使用本地用途前缀 `64:ff9b:1::/48` 的 IPv6-only 主机，经它转换的目标都会得到 `unsafe_address`。
  - 本设计不声称 NAT64 检查是“完整”的；维护者确认以上范围作为 ROADMAP R07-2“NAT64 按内嵌的 IPv4 判断”的实现范围。
- 普通私网、链路本地、组播、文档地址的拦截，以及重绑定后按实际 IP 检查的路径，评审没有发现漏检。

### 5.2 Server 保存时检查一次（release-decider S2 选 B）

1. **语法**（S3，规则放在 `internal/protocol`，与 Agent 共用）：
   - 字面 IP：用 `netip.ParseAddr`（它本身拒绝带前导零的 IPv4），不带方括号、不带 zone，保存为 `String()` 的规范形式；映射形式转成 IPv4；然后用 `PublicDestinationIP` 判断，同时判断族与勾选的子项是否匹配。
   - 主机名：
     - 只接受 ASCII（国际化域名填 punycode），统一小写，去掉末尾的点；
     - 总长 ≤253，每段 1–63 个字符，段首尾不能是 `-`，至少两段；
     - 最后一段必须含字母，不能是纯数字，也不能是 `0x` 开头的十六进制（防止 inet_aton 把 `0x7f.1`、`2130706433` 之类解析成 IP）；
     - 出现空白、`_ : / @ [ ] %`、`://` 等字符一律拒绝；
     - 拒绝这些名字和后缀：`localhost`，`.localhost .local .localdomain .internal .home.arpa .invalid .test .example .onion .alt`，整个 `.arpa`，以及 RFC 6762 附录 G 的 `.intranet .private .corp .home .lan`。
   - 端口：十进制 1–65535，不带符号，不带前导零。
2. **解析**（评审建议 4 的边界）：
   - 只对本次新增或改动的域名解析（最多 3 个），在事务外并行进行，**整次请求共用一个 2 秒期限**（不是每个域名 2 秒）；
   - 每个域名用 Server 本机解析器 `LookupNetIP("ip")` 同时查 A 和 AAAA；
   - 只要任何一侧返回了非公网地址（按所属族判断）就拒绝（`unsafe_address`），哪怕另一侧失败；
   - 两侧都失败（NXDOMAIN、超时）仍允许保存，由 Agent 兜底；
   - 全 Server 同时进行的 DNS 检查最多 4 个，已满时返回 `503 retryable`；
   - 解析结果不写入数据库，不写日志，不出现在错误响应里。
   - 界面要说明：这次检查只是提示性的，以 Agent 每次连接前的检查为准（Server 与 Agent 的解析器可能不同）。
3. 判断“是不是同一个目标”时，用规范化后的主机（和 TCP 端口）作为键。
4. 保存通过不代表持续安全。测试要覆盖“保存时解析到公网、探测时解析到私网”和“同一组解析结果里公网、私网混合”（两种顺序）。

### 5.3 Agent 每次连接前重新检查（防 DNS 重绑定）

- 现有 staged 路径已经满足：每次探测都重新解析 → 取第一个同族结果 → `qualityAddressPolicy` → 拨号字面 IP → `Dialer.Control` 再检查（只有 TCP；ICMP 直接向检查过的 IP 发包，不经过 Dialer）。
- **不安全就直接记 `unsafe_address`，不往后找安全的地址，连接失败时也不换下一个地址重试**（S5 条件 2）。
- 新 Agent 对收到的主机名先用 5.2 节的语法规则校验一次，不合格的整份配置都拒绝。

### 5.4 域名同时有 v4 和 v6 解析时

- v4 两个子项（TCP、ICMP）只解析 A，v6 两个子项只解析 AAAA，各自取第一个结果。
- 每个样本都记录 `resolved_ip`。多地址轮换会让历史混入不同 IP，这是可以接受的：“目标是否改变”看配置的地址，不看解析出的 IP，前端曲线也不按 `resolved_ip` 分段（S5 条件 3）。
- 域名没有 AAAA 时，v6 子项连续得到 `not_found`/`no_address`，按第 7 节显示为“目标异常（无 IPv6 解析）”。这些样本本来就不进失败率和丢包率的分母。

## 6. 自定义地区和 ISP 的输入限制

- 适用于自定义卡槽的 `region`、`isp`。内置卡槽只接受枚举值。
- 长度：1–32 个 Unicode 码点，并且 UTF-8 不超过 96 字节（与表的 CHECK 一致）。卡槽已填地址时两项都必填（`label_required`，维护者决定 P17；内置和自定义都适用）；地址为空时可以留空（迁移产生的空卡槽就是这样）。
- **原始请求体检查**（评审建议 3；release-decider D8）：Go 的 `encoding/json` 会把非法 UTF-8 和孤立的 `\uD800` 之类转义静默替换成 U+FFFD，所以只检查解码后的字符串做不到“拒绝、不静默修改”。保存接口在解码之前：
  - 先限制请求体大小（16384 字节），再对整个请求体做 `utf8.Valid`；
  - 用能识别 JSON 字符串（正确处理 `\\`）的扫描器检查转义：单独出现的 `\uD800–\uDBFF`，或不紧跟在高位代理转义后的 `\uDC00–\uDFFF`，整个请求返回 `400 invalid_encoding`；
  - 解码后再拒绝标签里的 U+FFFD，作为第二道防线；
  - 测试直接使用原始字节构造的请求体。
- 拒绝（不静默修改）：
  - 首尾空白：前端提交前先去掉，Server 收到带首尾空白的值直接拒绝，保证存储的值稳定；
  - 控制字符和格式字符：Unicode 类别 Cc、Cf（包括 U+200B–U+200D、U+2060、U+FEFF、双向控制符 U+202A–U+202E、U+2066–U+2069）、行分隔符和段分隔符 Zl/Zp、非字符；
  - 除 U+0020 以外的空白（包括 U+00A0、U+3000）；
  - 连续两个以上的空格。
- 不禁止尖括号等普通字符（防 XSS 靠输出方式，不靠输入黑名单）。不做 Unicode 规范化（不引入 `golang.org/x/text`），写法不同的字符串就是不同的标签。
- 自定义 ISP 写成“电信”也允许，仍然是用户标注；M18 中自定义 ISP 一律归入“其他”。
- **输出转义（防 XSS）**：
  - Server 用 `encoding/json` 输出（默认转义 `< > &`），设置 `Cache-Control: no-store`；
  - 前端只用 `textContent`、`title`/`aria-label` 属性、`<option>` 的 `textContent` 和 SVG `<title>` 的 `textContent`，禁止 `innerHTML` 和拼接 HTML（app.js 第 730 行的 `innerHTML` 只用于资源磁贴的静态标签，任何用户标签都不能传给它）；
  - 标签不进入日志、URL 和 CSS 选择器；
  - 阶段 D 在真实 DOM 里测试：标签为 `<img src=x onerror=…>`、含双向控制符的值，在卡片、弹窗、Mini 图例、详情页下拉里都原样显示为文本（或被 Server 拒绝），并断言没有生成任何新元素。

## 7. 状态判定

### 7.1 每个子项的状态（Server 计算 `status` + `condition`，前端只负责显示）

按以下优先级，取第一个命中的：

| 优先级 | 状态 | 条件 | 是否计入失败或丢包 |
|---|---|---|---|
| 1 | 设备已撤销/暂停 | 沿用现有逻辑 | — |
| 2 | 需升级 Agent / 协商中 / 不支持 | `agent_support` 不是 `user_targets` | — |
| 3 | 平台排除、存储压力 | 沿用 `excluded_reason`、`storage_pressure` | — |
| 4 | **已关闭**（R03-2） | 卡片总开关关闭。卡片显示“已关闭”，不再显示地区和“暂无有效 RTT” | 否 |
| 5 | **未配置目标** | 卡槽地址为空 | 否 |
| 6 | **未启用** | 卡槽未勾选或子项未勾选；卡片显示“未启用”（维护者决定 P9） | 否 |
| 7 | **本机无 IPv6** | v6 子项，且设备级快照 `ipv6_address=none`（见 7.2）。排在“不支持 ICMP”之前，避免被它遮盖 | 否 |
| 8 | **不支持 ICMP** | ICMP 子项且 lane capability `supported=false`（例如容器内 CAP_NET_RAW 受限）。勾选框禁用；已保存的勾选保留但不调度 | 否 |
| 9 | **目标异常** | 见 7.3（要求最近事件仍在新鲜度预算内） | 否（显示层；统计口径不变） |
| 10 | 正常、失败、过期、未知 | 沿用 `cardCurrent`（staged 当前样本、新鲜度预算、配置不匹配；比较对象是测量版本 `config_revision`） | 按现有口径 |

### 7.2 本机无 IPv6（release-decider T5 + D4 选 C）

- **只看地址，不看错误码**：有地址但没有路由时照常探测、照常计失败，如实反映“IPv6 坏了”。不按 ENETUNREACH 归类（会把路由临时撤销这类真实故障藏起来）。
- **区分“从未有过”和“运行中失去”**（D4，回应评审 N2）：
  - Agent 进程启动后，如果 5 分钟内**每一次**扫描都成功、且都没有看到可用的 IPv6 地址，才上报 `ipv6_address:"none"`。启动后头 5 分钟上报 `unknown`，不会“启动即确认”；
  - 本进程一旦看到过可用的 IPv6 地址，之后就不再上报 `none`；地址后来消失，按故障处理（v6 子项照常探测、照常计失败）；
  - 地址一出现，立即改报 `present`，授权重算自动重开 v6 通道（4.3 节），用户不需要重新操作。
- **扫描**：每次上报前扫描一次（默认 10 秒）。计入“可用地址”的条件：接口处于 Up 且不是回环；地址是全局单播（2000::/3）或 ULA（`fc00::/7`，Podman 可能通过 NAT66 用 ULA 出网）；在 Linux 上读取 `/proc/net/if_inet6`，排除 tentative 和 dadfailed 状态的地址。隧道接口上的全局地址同样计入。IPv6 被整个禁用（没有 `/proc/net/if_inet6` 或没有任何 v6 地址）算作“没有”。**扫描出错算 `unknown`**，不能触发 `none`。
- **传输**：使用单独的族级字段 `ipv6_address`（4.2 节），不把 lane 的 `Supported` 改成 false，这样 socket 能力（ICMP 是否支持）和地址可用性互不遮盖。只有协商之后才发送；旧 Agent 不发送，行为与现在一样。
- `ipv6_address=none` 是授权重算的正面证据：关闭 v6 通道，不计失败。

### 7.3 目标异常（release-decider T6 + D2；评审 M2）

目标是每张卡片各自的，不能用“所有 Agent 都失败”来判断。“目标异常”是**从这台 Agent 本机视角看到的解析或地址不可用提示**，不是全网证实的目标故障（评审建议 2）。只影响显示，失败率和丢包率的口径不变。

**地址诊断事件**（不改 `ProbeComplete`、`ConnectAttempted`、Echo 的现有语义）：
- 评审指出：TCP 的 `unsafe_address`、ICMP 的 DNS 失败和 `unsafe_address` 现在都是 `ProbeComplete=false`，而 ICMP 又要求 `ProbeComplete == WindowComplete`。所以不能按“完成的探测”计数，也不能把这些样本改成 `ProbeComplete=true`。
- 改为单独定义“地址诊断事件”：staged 样本中 `dns_outcome ∈ {not_found, no_address}`，或 `error_code = unsafe_address`，不论 `ProbeComplete` 是什么。
- `not_found` 是新的 DNS 结果值（Go `IsNotFound`，即 NXDOMAIN 或该族无记录；现在被归入 `dns_error`），只在协商后发送。`ValidateDetails` 要同时改三处：`DNSOutcome` 白名单、`ErrorCode` 白名单、TCP“DNS 阶段结束”分支（`network_quality_details.go` 第 83–125 行，要求 `ErrorCode == DNSOutcome`）。

**判据**：
| 判据 | 是否采用 | 规则 | 误判风险 |
|---|---|---|---|
| (1) 域名不存在 | 采用 | 地址诊断事件 `not_found` | 本机解析器劫持或分离视图返回 NXDOMAIN 时会误判为目标异常（见下方“解析器排除”） |
| (2) 该族无解析结果 | 采用 | `no_address` 或 `not_found`（例如域名没有 AAAA）；显示“目标异常（无 IPv6/IPv4 解析）” | DNS64 或解析器过滤 AAAA 时会误判。影响小，样本本来就不进分母 |
| (3) 解析到非公网地址 | 采用 | `unsafe_address`；字面 IP 的情况保存时就已拒绝 | 几乎确定。例外：使用 `64:ff9b:1::/48` 的 IPv6-only 主机（5.1 节的已知限制）；以及只劫持某一个域名的路由器 DNS |
| (4) TCP 连续 refused | 不采用 | 照常计入 Connect 失败（分母 +1） | RST 可能来自路径上的设备注入，正是要测的东西；排除它与 M14-C 的“分母是实际的 Connect 尝试次数”冲突 |
| (5) ICMP 长期 0 回包但同地址 TCP 成功 | 不采用 | 照常计入丢包（真实发送数和接收数） | ICMP 被限速或屏蔽是路径的属性；排除它与 M14-C 冲突 |
| (6) 超时、SERVFAIL、DNS 超时 | 不采用 | 照常显示为失败。具体分母：TCP 的 DNS 超时不增加 Connect 尝试；ICMP 没有发出 Echo 时不增加真实发送数 | 无法区分目标故障和路径故障 |

**计数规则**（D2）：
- 事件按 `started_at`、`seq` 排序，只计入：同一 `target_id` + 同一 `slot_revision` + 当前会话（epoch/session_id）+ `started_at` 在当前开放区间的 `start_at` 之后。这样关闭后重开、Agent 重启、旧队列补传的旧错误都不会算进当前状态。
- 最近 **3 个**样本都是地址诊断事件（三类可以混合计数），就显示“目标异常”，原因取最近一次的事件；
- 最近一次事件必须仍在该通道的新鲜度预算之内，否则落到“过期”（避免离线的通道在原始样本保留的 8 小时里一直显示异常）；
- 遇到任何其他结果（成功、timeout、refused、`dns_error`、`dns_timeout`、`canceled`、未执行）立即清除。
- **解析器排除**：同一 Agent、同一会话内，如果 ≥2 个**不同主机名**的通道同时满足“连续 3 次 + 新鲜”的条件（同一个主机名出现在几个卡槽里只算一次），这些通道都不标“目标异常”，按普通 DNS 失败显示（很可能是本机解析器的问题）。字面 IP 通道不受影响。
  - 代价：两个不同域名恰好同时真实下线，会被压成普通 DNS 失败；只有一个域名时无法区分。
  - 不新增“本机 DNS 异常”状态，它不在 R07-6 的列表里。
- 计算位置：Server 在读取时，根据最近的 staged 样本（`quality_raw.details_json`，保留 8 小时）计算，作为 `lanes[].condition` 返回。

### 7.4 卡片级文字

- 总开关关闭：“已关闭”。
- 3 个卡槽都没有地址：“未配置目标”。
- 旧 Agent：“需升级 Agent 才能使用自定义目标”。新 Agent 重启后尚未完成协商：“正在连接…”（约一个上报周期）。
- 其余按子项状态显示。

  - **没有按时间过期**：`tcp_mini_high` 的清理界限是 `last_high − 72h`（只删比最近一次高值早 72 小时以上的记录），不是“当前时间 − 72h”；代码注释也写明空闲时间不会让告警证据过期。所以如果之后没有任何 IPv4 TCP 正常分钟（例如总开关关闭、换成只有 ICMP 的目标、Agent 离线），告警会一直显示，没有上限。

    - **有开着的 TCP 线路时**，告警行为与现在相同；提示文字如实描述：“告警持续到之后某一天出现正常 TCP 分钟为止，可能来自已更换的目标”，并显示告警来源日（`source_day`）。
    - “开着的 TCP 线路”的判定：该 Agent 存在 IPv4 TCP 的开放授权区间（`quality_intervals` 中 `family='ipv4'`、`protocol='tcp'`、`end_at IS NULL`），且设备未撤销、未暂停。只看 IPv4，是因为 TCP Mini 本来只汇总 IPv4 TCP 目标：只开着 IPv6 TCP 子项时，TCP Mini 既没有新数据、也无法解除旧告警，所以同样显示“无当前 TCP 检测”。
    - 判定由 Server 做：`GET …/v3/tcp-mini` 的响应增加只读字段 `current_tcp`（布尔），在同一个只读事务里按上面的规则计算；`state`、`coverage`、`level_ms` 等现有字段的含义不变。前端只看这个字段，不自行推断。旧前端会忽略新字段（宽松解码），不受影响。
    - 升级后：迁移 34 结束所有区间并关闭总开关，所以升级后、用户重新配置并开启之前，v1.0.4 留下的旧告警**不会显示**，显示“无当前 TCP 检测”；用户开启 IPv4 TCP 检测后，按原有规则显示（旧证据仍可能显示，直到之后某一天出现正常分钟）。
  - 阶段 B 加一个现状契约测试：形成有效高值后停止检测，超过 72 小时且没有新的正常分钟，`TCPMini` 仍返回 `state: alert`（证据保留），同时 `current_tcp=false`。

- **历史目标**：`SELECT id, payload, created_at, created_revision, first_active_at, retired_at FROM quality_targets WHERE agent_id=?`（包括已退役的），加上 `quality_series`/`quality_buckets` 的存在性和时间范围。

- **R07 中已退役目标的可见范围**（评审 M6；release-decider D10 选 B）：R07 只保证已退役目标的历史留存，并且可以通过 `v3/history`、`v3/card-history` 按已知 target_id 读取（由存储和 API 测试证明）。**界面上浏览已退役目标交给 M14**，符合 ROADMAP R07-7“旧数据保留，供 M14 查看”。用户可见的影响：升级到 v1.0.5 后，设备详情页的网络页签只列当前目标；v1.0.4 内置目标的历史在 M14 之前没有界面入口（数据仍在，30 天内的桶按现有规则保留）。
- **按地区和 ISP 筛选（A3/A4）——维护者覆盖 T2 后的影响**：
  - 筛选用的地区和 ISP 选项来自 `quality_slot_settings` 的**当前**标签（含自定义值）；每个 target 通过 `slot` 归到卡槽，再取该卡槽的当前标签。等价于“先按卡槽筛选，再把卡槽当前的标签当作它全部历史的标签”。

    - **信息损失**（无法弥补）：旧标签没有保存，M14 不能按“测量当时的标签”筛选，也不能把“曾经标为同一地区、后来改了标签”的历史找回来；
    - **查询能力**（可以做）：按当前标签相同的多个卡槽（包括不同 Agent 上的卡槽）做并列或聚合比较是可以的。
  - 地址清空、标签留空的卡槽，历史显示为“卡槽 N（未标注）”，筛选时归入“未标注”。
  - M14 界面要写明：“地区和 ISP 为卡槽当前的用户标注，修改后历史随之改名”。
  - M18 的“按 ISP 评价”同样按当前标签，改标签会改变历史评价的归属；M18 设计时需注意。
  - 如果以后需要“测量当时的标签”，需要新增标签历史表（另一个迁移），不在 v1.0.5 范围内。
- **配置版本**（评审建议 8）：
  - `created_revision` 是目标**创建时**的测量版本。总开关关闭时也可以保存、创建目标，之后开启才第一次授权，所以它不等于首次生效的版本；首次生效时间看 `first_active_at`。
  - 历史桶带 `config_revision/slot_revision` 的最小值和最大值（`quality_buckets` 已有），M14 只能显示每个桶的**版本范围**，不能恢复已经合并进同一个桶的逐版本数据。
  - `quality_intervals` 在结束后 48 小时就删除，**不能**作为 30 天的版本历史来源。M14 若需要精确的逐版本时间段，要在 M14 的设计阶段另行提出（不在 v1.0.5 的迁移范围内）。
  - 设置版本 `settings_revision` 只用于乐观锁，不进入样本和桶。
- 现有历史接口按 target_id 读取，对已退役的 target 同样可用，R07 不改它们的契约（只在返回的 `target` 里补上卡槽当前标签）。
- “不改动 M14 详情页的图表”：R07 只改详情页目标下拉的文字，不改图表代码，也不改目标来源。

### 11.1 实现边界备忘（第 3 版复核的建议 G1–G6）

以下是复核提出的实现细节，不改变已定方案，在对应阶段实现时落实并测试：
- **G1 协商快照的事务边界**（阶段 B）：报告后的授权重算事务要重新读取并核对最新的 `agent_state`/`quality_capability` 的 epoch、session_id 和报告序号，旧请求的延迟处理不能覆盖新会话或后到的撤销；重算失败时由后续带完整能力的报告重试，没有建立授权区间时不下发 active 目标；补交错授予/撤销、换会话、注入一次重算失败后恢复的测试；补“已安装用户目标配置后，拉取请求缺头”的结果（下发停用配置，Agent 停止）。
- **G2 IPv6 `unknown` 的时间语义**（阶段 C）：扫描出错后重新开始累计“连续 5 分钟扫描成功且没有地址”的观察期，而不是永远不能确认 `none`；已确认 `none` 后扫描出错改报 `unknown` 时，设备级快照保留最后一次确定的 `none`（`unknown` 不触发任何变更）。
- **G3 迁移执行细节**（阶段 B）：`settings_revision` 先以 `DEFAULT 0` 加列再回填（2.2 节已改）；各层先读出旧版本号和旧标签来源，再清空遗留列；校验显式包含全部 `quality_config.enabled=0`、`quality_slots.enabled=0`、`quality_slots.target_id IS NULL`、`quality_capability.user_targets=0`；从未配置、也没有 slot/开放区间的 Agent 不建行，读取时按默认 3 个空卡槽处理；失败注入同时断言 DDL、R23 的列和数据、`schema_migrations` 都回到起点；补“schema 34 被 v1.0.4（schema 32）二进制直接拒绝”的用例。
- **G4 时限的概括**：1.4 节的“约 10 + 30 秒”以链路正常、请求成功为前提；5 分钟是拉取退避间隔的上限，不是停止的上限；“6 小时内仍可被接受”还须满足 1.2 节的全部条件；Server 升级后网络质量停止，指 Agent 恢复通信并收到有效停用配置之后。
- **G5 前端适配与缓存身份**（阶段 D）：合成的 ICMP target `port=0`，不复制卡槽的 TCP 端口；测量身份和缓存键不包含标签，`latency-mini` 的 `identity()`/`normalize` 中对 `region` 的比较要去掉；内部所有使用 `revision` 的地方改为 `config_revision`；真实 DTO 测试覆盖“旧标签的异步响应 + 已缓存历史 + 新标签”同时出现。
- **G6 RFC 7050 刷新的实现**（阶段 C）：现有 `LookupNetIP` 不返回 TTL，所以刷新策略写明为“有上下限的固定刷新”（启动时一次，之后每 10 分钟，失败按退避，最长 1 小时），不声称严格遵守 TTL；单次查询超时 5 秒；结果去重并最多保留 8 个前缀；探测读取不可变的前缀快照，DNS 查询不在 `Dialer.Control` 中同步执行。
